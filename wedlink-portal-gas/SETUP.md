# WEDLINK 支店ポータル（全支店横断WEBアプリ版）セットアップ手順

`ROW_fixed.gs`（ROW支店専用スクリプト）を、世界中の支店へ**コードを一切書き換えずに**横展開できるように
再設計したものです。関東手配課・関西手配課どちらでログインしても全支店を横断閲覧・操作でき、
支店ユーザーは自分の支店のデータのみアクセスできます。

## ファイル構成

- `appsscript.json` — マニフェスト（Webアプリとして "全員アクセス可" で公開する設定）
- `Code.gs` — サーバーサイドロジック（認証・データ操作・検索・メール通知・アラート）
- `Index.html` / `Stylesheet.html` / `JavaScript.html` — スマホ対応のフロントエンド（1画面SPA）
- 本ファイル — セットアップ手順・設計メモ

## デプロイ手順

1. Googleスプレッドシートを新規作成する（IDを控えておく：`.../d/【ここ】/edit`）。
2. 拡張機能 → Apps Script を開き、このフォルダの5ファイルの中身を同名で作成・貼り付ける。
3. `Code.gs` 冒頭の `SPREADSHEET_ID` に手順1のIDを設定する。
4. 関数選択で `setupPortal` を実行する。
   - 「支店マスタ」「プランマスタ」「オプションマスタ」「撮影場所マスタ」「スタッフマスタ」「定型文マスタ」
     「セールマスタ」「予約一覧」「やり取り履歴」「過去一覧」「ステータス変更履歴」「メモ履歴」「手配履歴」の
     13シートと、24支店＋関東/関西手配課アカウントのサンプル行が自動作成されます。
   - **この関数は何度実行しても安全です。** 既存のシートがある場合は、不足している列だけを
     右端に追加します（既存のデータ・入力済みの値・列の並びは変更しません）。
   - **コードを新しい版に差し替えたときは、必ずもう一度 `setupPortal` を実行してください。**
     機能追加で増えた列（請求番号／現地記入欄／送信者ロール／既読者氏名など）が
     シートに無いままだと、その項目の保存時にエラーになります。
5. 「支店マスタ」シートで各行の **ログインパスコード** と **通知先メール** を実際の値に書き換える。
6. 「プランマスタ」「オプションマスタ」シートに、支店ごとのプラン名・オプション名を入力する
   （書式は下記「マスタ管理について」を参照）。
7. 「デプロイ」→「新しいデプロイ」→種類「ウェブアプリ」
   （実行するユーザー：**アクセスしたユーザー** ／アクセスできるユーザー：**組織内（his-world.com）の全員**）。
   ※この設定は「誰が変更・送信したか個人名を記録する」ために必須です。詳しくは下記
   「13. メッセージ・変更履歴に個人名を記録」を参照してください。
8. 発行されたURLを各支店・関東手配課・関西手配課の担当者に配布する（そのままログイン画面になります）。
9. 関数選択で `setupTriggers` を実行し、日次のトリガーを設定する。
   - `archivePastReservations`（2時）／`checkAlerts`（8時・撮影45日前）／
     `checkDeliveryAlerts`（8時・納品期限）／`checkUnansweredAlerts`（9時・未返信リマインド）
10. （任意）Googleフォームで『同意書』を回収する場合は、関数選択で `setupConsentFormTrigger` を実行する。
    事前準備は「39. 同意書（Googleフォーム連携）」を参照。
11. （任意）Googleフォームで当日の髪型・メイクの希望などのアンケートを回収する場合は、関数選択で
    `setupSurveyFormTrigger` を実行する。事前準備は「46. アンケート回答の反映（Googleフォーム連携）」を参照。
12. （任意）現地スタッフ手配メール（カメラマン・ヘアメイク等）を使う支店は、ログイン後「設定」画面から
    宛先を登録し、支店マスタの「手配メール機能」をTRUEにする。詳しくは「45. 現地スタッフ手配メール」を参照。

## マスタ管理について（支店・プラン・オプション）

支店・プラン・オプションの登録／編集は、**アプリの画面ではなく裏のスプレッドシートを直接編集する**運用です。

- **支店マスタ**：支店を追加する場合は1行追加するだけ（コード変更・再デプロイ不要）。列の意味は本ファイル末尾の表を参照。
- **プランマスタ／オプションマスタ**：`支店コード / 名称 / 有効` の3列。支店ごとに複数行登録できます。
  ここに登録した内容が、案件詳細画面の「プラン名」「オプション」欄の選択肢としてそのまま反映されます
  （画面側は読み取り専用のプルダウンです）。

なお `Code.gs` にはこれらのマスタを書き込むAPI（`apiSaveBranch` / `apiSetBranchActive` /
`apiSavePlanItem` / `apiSaveOptionItem`）も残してあります。今後アプリ内に管理画面を作りたくなった場合は
そのまま利用できます。

## 今回追加・変更した仕様

### 1. 日本側は「関東手配課」「関西手配課」の2アカウントに分離
- ロールは `BRANCH`（支店）と `JP`（日本側）の2種類。関東・関西どちらでログインしても**権限は同じ**で、
  全支店を横断して閲覧・操作できます。
- 案件一覧・検索画面の「表示範囲」チェックボックスで、全国／関東手配課／関西手配課／支店ごとを
  自由に組み合わせて絞り込めます（複数選択可）。
- ログイン画面はプルダウン選択式です（コードを覚えて入力する必要はありません）。
- **メッセージの宛先は、ログインしている拠点ではなく「開いている案件の支店」で決まります。**
  例：関東手配課でログインしてローマの案件を開き、メッセージを送信すると、宛先はローマ支店の
  通知先メール（支店マスタに登録済み）になります。関東／関西の違いは、日本側からのメッセージが
  どちらのチームの担当分として履歴に残るかだけです。

### 2. ステータス（STS）：コードと編集ルール
`RQ` / `OK` / `CHK` / `CR` / `FN` / `CW` / `NC` / `UC` / `CF` の9種類をそのまま選択式で使います
（和訳ラベルは表示しません）。**日本側と支店側は互いの相手のステータスを直接編集できません。**

コードの意味（運用ヒアリングに基づく）：
- `RQ`＝予約依頼、`CHK`＝空き確認のみ、`NC`＝依頼なし／状態リセット
- `UC`＝現地に空きがない（`RQ`・`CHK`に対する支店側の回答）
- `CR`＝日本側が既存予約のキャンセルを依頼（キャンセルリクエスト）
- `CW`＝キャンセル成立・チャージなし、`CF`＝キャンセル成立・キャンセルチャージあり（`CR`に対する支店側の回答）
- `OK`＝空きあり、`FN`＝最終確定 — 運用上の到達状態

編集ルール：
- **STS(JP側)** は日本側のみが編集できます。いつでも自由に値を選べます。
- **STS(支店側)** は支店側のみが編集できます。ただし対になる **STS(JP側) の現在値**によって
  選べる範囲が変わります。
  - STS(JP側) が `NC`・`RQ`・`CHK` のとき → 支店側は自由にどのコードでも選べます（空きがなければ`UC`など）。
  - STS(JP側) が `CR` のとき → 支店側は `CW`（チャージなし）か `CF`（チャージあり）のみ選べます。
  - それ以外（`OK`・`FN`・`CW`・`UC`・`CF`・未設定）のとき → 支店側は変更できません（ロック）。
- このルールはメインのSTSだけでなく、**OP1〜OP5のオプションごとのSTS(JP側)／STS(支店側)にも
  同じように適用**されます（オプションごとに独立してゲートされます）。

### 3. 予約済み案件内の変更は「保存のみ／メッセージのみ送信／変更＋メッセージ送信」の3択で確定
既存予約内のほぼ全ての項目（ステータス・オプション・撮影日・挙式日・ホテル・プラン・共有メモ…
DriveフォルダURLを除く全て）は、その場で自動保存せず、画面下部の3つのボタンのいずれかで確定します。

- **保存のみ（通知しない）**：入力中の変更を保存するだけで、相手への通知（履歴ログ・メール）は発生しません。
  共有メモの更新など、相手に知らせる必要がない変更に使います。
- **メッセージのみ送信**：入力中の変更フィールドには触れず、メッセージだけを1件の履歴・メールとして送信します
  （変更は保存されずに残ったままなので、別途「保存のみ」か「変更＋メッセージ送信」で確定してください）。
- **変更（＋メッセージ）を決定して送信**：入力中の全ての変更内容を保存し、任意で書いたメッセージと合わせて
  1回の履歴ログ・1通のメールとして相手に通知します（例：日本側が新しいオプションを追加してSTS(JP側)を
  `RQ`にする、という一連の変更を1回の送信で支店へ通知）。

サーバー側APIは `apiSaveFieldsQuiet`（保存のみ）と `apiCommitChanges`（メッセージのみ／変更＋メッセージ、
`changes`が空ならメッセージのみとして扱う）の2つに統一しています。

### 4. 案件番号（管理番号）は支店ごとに一意なプレフィックス＋連番
- 支店マスタの「案件番号プレフィックス」列で、支店ごとに管理番号の先頭文字を設定します。
- **ローマ支店は既存運用のため `R` のまま固定**（変更しないでください）。他の支店は未使用のため、
  デフォルトで支店コードそのもの（例: `VIE` → `VIE-001`）を使う設計にしています。
- 連番はその支店の行だけを数えて採番するため、支店が何十件に増えても番号が衝突したり
  巻き戻ったりしません。プレフィックスの重複は支店保存時にサーバー側でチェックします
  （現在はマスタ書き込みAPI側のチェックのみのため、スプレッドシートを直接編集する場合は
  プレフィックスが重複しないよう手動で確認してください）。

### 5. 撮影日FIX・挙式日FIXの変更ログ
撮影日FIX・挙式日FIXも上記3択の対象です。「変更（＋メッセージ）を決定して送信」を選ぶと
「変更前 → 変更後」が履歴・メールの本文に自動で含まれます（「保存のみ」を選んだ場合は通知されません）。

### 6. プラン・オプションは支店ごとにマスタ管理
「プランマスタ」「オプションマスタ」シート（国・支店ごとに内容が異なる前提）に登録した内容が、
案件詳細の「プラン名」「オプション」欄でプルダウンとして選べます。

### 7. お名前・請求先・日本支店名
- `新郎名（ローマ字）` `新婦名（ローマ字）` の2項目で管理します。
- `請求先`（北海道／東北／関東／中部／関西／中四国／九州の7区分）を追加しました。
- `日本支店名`（案件を扱う日本側の店舗名）と `店舗／担当（現地）`（海外支店側の店舗・担当者）を
  別項目として管理します。

### 8. 案件番号・チャレンジ番号を常に表示
一覧・検索結果・詳細画面のいずれにも「管理番号」「CHG NO（チャレンジ番号）」を常時表示しています。

### 9. メッセージ・共有メモ
- やり取り履歴（メッセージ）は新しい日時が上に来る順で表示します。
- 「共有メモ」欄：支店・日本側どちらも自由に書き換えられる、送信操作を伴わないメモ欄です。

### 10. 検索機能
検索画面で以下の条件を組み合わせて検索できます（すべて任意・AND条件）。
- 管理番号（部分一致）／チャレンジ番号（部分一致）
- お名前（ローマ字・新郎新婦どちらでも部分一致）
- 国・都市（日本側ユーザーのみ表示）
- **STS(JP側)／STS(支店側)**（完全一致）
- 撮影日FIX または 挙式日FIX の期間（開始日〜終了日）
- 「過去一覧（アーカイブ済み案件）も含める」チェック
- 表示範囲チェックボックス（日本側ユーザーのみ。全国／関東／関西／支店ごと）

### 11. 一覧のキャンセル表示切り替え
案件一覧は既定で「生きている（キャンセルでない）」案件のみ表示します。
STS(JP側)またはSTS(支店側)が `CW` の案件は、「キャンセル（CW）済みも表示する」チェックを
入れたときだけ表示されます（日本側・支店側どちらの一覧にも適用）。

### 12. 過去一覧への自動移動ルールを拡張
撮影日FIXまたは挙式日FIXのいずれかが**今日より過去になった時点で**、ステータスに関わらず
自動的に「過去一覧」へ移動します（従来は「STSがFNかつ日付超過」のみが対象でしたが、
日付が過ぎたら自動的に過去扱いにする、という単純なルールに変更しました）。
`CW`（キャンセル）の案件は日付に関係なく即座に過去一覧へ移動します。
過去一覧に移動した案件も、検索・詳細閲覧・編集・メッセージ送信は引き続き可能です。

### 13. メッセージ・変更履歴に個人名を記録
支店・日本側とも、各拠点で使うGoogleアカウントは「氏名@his-world.com」形式（氏名部分がメールの
ローカル部）で運用されている前提で、`Session.getActiveUser().getEmail()` から実際の担当者名を
取得し、「氏名（支店名／チーム名）」の形でメッセージ送信者・変更者として履歴とメール本文に残します。

これを機能させるため、Webアプリのデプロイ設定を
**「実行するユーザー：アクセスしたユーザー」「アクセスできるユーザー：組織内（his-world.com）の全員」**
に変更しました（`appsscript.json` の `executeAs: USER_ACCESSING` / `access: DOMAIN`）。

- 海外支店の担当者も含めて **全員が his-world.com のGoogleアカウントでログインした状態でURLを開く**
  必要があります。もし一部の支店にhis-world.comアカウントがない場合は、個人名の記録を諦めて
  従来どおり `executeAs: USER_DEPLOYING` / `access: ANYONE`（支店コード＋パスコードのみで誰でもアクセス可）
  に戻すことも可能です。その場合は個人名は記録されず、支店名／チーム名のみが表示されます
  （`getActiveUserName_()` が空文字を返すため自動的にフォールバックします）。
- 支店コード＋パスコードのログインは、この変更後も**役割（どの支店／どのチームとして操作するか）を
  決めるためにそのまま残しています**。個人のGoogleアカウントだけでは「今どの支店として動いているか」
  は判別できないためです。

### 14. ステータス変更履歴（誰が・いつ・何を変更したか）
STS(JP側)・STS(支店側)（メイン・オプション共通）を変更すると、新設の「ステータス変更履歴」シートに
`管理番号・フィールド名・変更前・変更後・変更者・日時` が自動で記録されます。「保存のみ」で変更した
場合も記録されます（相手への通知が発生しないだけで、監査ログとしては必ず残ります）。

案件詳細画面では、各STSの値の下に「履歴」リンクがあり、タップするとそのフィールドの変更履歴
（新しい順）がその場に展開されます（`apiGetFieldHistory` で取得）。

### 15. 一覧の並び順
案件一覧は撮影日FIXが**今日に近い日付から順**に並びます（未定の案件は末尾）。

### 16. 支店側の画面でもステータス・オプションを編集できます
支店ロールでログインすると、STS(支店側)・各オプションのSTS(支店側)・オプション名は、
「2. ステータス（STS）：コードと編集ルール」に書いたゲート条件を満たしていれば選択式で編集できます。
ロックされている場合は `🔒 現在の値（STS JP: 現在のJP側の値）` という形で理由も表示されます
（以前はロック時の表示が単なる `-` で、なぜ編集できないのか分かりづらかったため改善しました）。
また、`.status-row` / `.status-card` 用のCSSが抜けていて見た目が崩れていた不具合も修正しています。

すぐに動作を確認したい場合は、STS(JP側)が `NC`・`RQ`・`CHK` のいずれかになっている案件（新規作成
直後の案件は既定でSTS(JP側)＝`RQ`です）を支店側で開いてください。

### 17. 案件一覧・検索結果に「担当（関東手配課／関西手配課）」を表示
"管轄" 列の値をもとに、一覧カード・検索結果カード・詳細画面のいずれにも「担当: 関東手配課」のように
表示するようにしました（支店側の画面でも表示されます。従来はこの情報がどこにも表示されていませんでした）。

### 18. 撮影希望場所は任意入力＋マスタ候補（datalist）
「撮影希望場所」は国・地域によって全く異なるため、プラン名のような強制の選択式にはせず、
自由入力の欄に変更しました。新設の「撮影場所マスタ」シート（プランマスタ・オプションマスタと同じ
`支店コード・名称・有効` の構成）に登録しておくと、入力欄で候補として選べます（`<input list>` +
`<datalist>`）。候補になくても自由に文字を入力して保存できます。

### 19. 請求番号（現地支店が名称を変更できる欄）
現地支店が使う「請求番号」欄を追加しました。この欄の**名称そのもの**を支店ごとに変更できるよう、
支店マスタに「請求番号欄名称」列を追加しています（例：支店によって呼び方が違う場合に対応）。
未設定の場合は既定で「請求番号」と表示されます。値の入力・変更は他の項目と同じく3択（保存のみ／
メッセージのみ送信／変更＋メッセージ送信）で確定します。

### 20. 現地記入欄（当日の運用情報）
案件詳細に「現地記入欄」タブを新設し、以下の項目を追加しました。いずれも自由入力で、
他の項目と同じ3択の保存・通知フローに従います。
- 当日の担当／ヘアメイク／カメラマン／アシスタント／配車時間／メモ（現地用）

### 21. 撮影日◯日前アラートを45日前に変更
従来40日前だった「STS未完了アラート」を **撮影日の45日前** に変更しました
（`checkAlerts` トリガー、`ALERT_DAYS_BEFORE` 定数）。

### 22. 納品期限アラート（新設）
撮影日から一定日数が過ぎてもDriveフォルダURL（納品）が未登録の案件を、日本側（管轄の手配課）へ
メールで通知する `checkDeliveryAlerts` を新設し、`checkAlerts` と同様に毎日8時に実行するトリガーを
`setupTriggers()` に追加しました。日数（何日で通知するか）は**国・支店ごとに異なる**という要件のため、
支店マスタの「納品期限日数」列で支店ごとに設定できます（未設定の場合は既定30日 `DELIVERY_ALERT_DEFAULT_DAYS`
にフォールバック。0を設定した場合は「撮影翌日から」通知します）。

通知のタイミングは、期限日に1通 → 未納品が続く場合は7日おきに再通知 → 期限日から28日経過で打ち切り、
としています（期限当日にトリガーが実行できなかった場合でもアラートが消えないようにしつつ、
毎日届いたり過去案件から延々と届いたりしないようにするため）。

なお、この関数は**「予約一覧」と「過去一覧」の両方**を走査します。撮影日を過ぎた案件は翌日には
過去一覧へ自動移動する仕様のため、予約一覧だけを見ていると「撮影日から30日後」の判定時点で
対象案件が1件も残っておらず、アラートが永久に飛びません（実際にその不具合があり修正済みです）。

### 23. 案件詳細をタブ構成に変更

迷わず登録できるようにしました。このタブだけは他の項目と違い、入力すると即座に相手へ通知されます

集計対象は**現在進行中（＝過去一覧に移っておらず、STS(JP側)・STS(支店側)ともにCW＝キャンセル成立でない）**

### 28. 未読判定を高速化（予約一覧の未読フラグ列）
当初は案件一覧を開くたびに「やり取り履歴」シートを**全件読み込んで**未読を判定していました。
履歴はメッセージ・変更・案件作成のたびに増え続けるため、24支店で運用を続けると
一覧の表示が確実に遅くなる構造でした。

そこで予約一覧（および過去一覧）に **「未読 JP」「未読 支店」** の2列を追加し、
- メッセージ・変更・DriveフォルダURL更新・新規案件作成のとき → 相手側の未読フラグを立てる
- 既読チェックを入れた／外したとき → その案件の履歴だけを見てフラグを計算し直す

という運用に変更しました。案件一覧はこの列を読むだけになり、履歴の件数に関係なく一定の速度で表示されます。

- この2列は**システムが自動で管理する列**です。画面からは編集できません（手で書き換えないでください）。
- 既存のスプレッドシートに列を追加した直後は全て空欄になるため、`setupPortal` の最後で
  `rebuildUnreadFlags()` を自動実行し、履歴から実態を計算して反映します。
- 万一フラグの状態が実態とずれた場合は、スクリプトエディタから **`rebuildUnreadFlags`** を
  単体で実行すれば、履歴を元に全件を計算し直せます（何度でも安全に実行できます）。
- 列がまだ無い旧シートで動かした場合は、従来どおり履歴を走査する方式に自動でフォールバックします。

### 29. 定期処理の障害通知とログ（新設）
当初は定期処理（アラート・アーカイブ）に例外処理もログ出力も無く、
**1行でも不正なデータがあるとその時点で処理が止まり、以降の案件のアラートが送られない**、
しかも**失敗しても誰にも通知されない**状態でした。

- すべての定期処理を共通ランナー `runTrigger_()` で包み、実行結果を必ずログに残すようにしました。
- 各処理の中では **行単位でも例外を捕捉**します。1件の案件でエラーが起きても、
  残りの案件の処理は続行されます。
- エラーが1件でもあれば、`SYSTEM_ALERT_EMAIL`（既定 `it-planning@his-world.com`）へ
  **障害通知メール**を送ります。本文には発生日時・処理時間・エラー件数に加えて、
  **どの案件（管理番号）で何が起きたか**とスタックトレースが含まれます。
- 定数 `SYSTEM_ALERT_EMAIL` は名前のとおりシステム障害の通知先として機能するようになりました
  （以前は手配課メールの最終フォールバック先としてしか使われていませんでした）。

あわせて、`archivePastReservations` は1行ずつ削除する処理のため、1回の実行で移動する件数に
上限（`ARCHIVE_MAX_ROWS_PER_RUN` = 500件）を設けました。上限に達した場合は残りを翌日の実行で
処理します（取りこぼしにはなりません）。長期間トリガーが停止していた後の再開時などに、
実行時間制限（6分）へ達するのを防ぐためです。

### 30. 未返信リマインド（放置案件の自動督促）

### 38. 実績データの書き出し（JPのみ）
統計は画面表示のみで、経理や社内報告へ渡すには手作業の転記が必要でした。

検索画面に **「この条件でスプレッドシートに書き出す」** ボタンを追加しました。検索とまったく同じ

`書き出し_yyyyMMdd_HHmmss` という新規シートとして出力します。区分（予約一覧／過去一覧）・支店名・国の

### 39. 同意書（Googleフォーム連携）
お客様に別途Googleフォームで『同意書』に回答してもらう運用があり、その結果（記入済みか否か）を

案件詳細（「予約内容」タブ）に **「同意書」** の欄を追加しました。支店マスタの新設列
**「同意書必須」** をTRUEにした支店（例：ローマ支店）は、未回収のときに赤字で警告表示されます。

反映方法は2通りです。
- **手動**：画面のチェックボックスをオン/オフし、通常の3択（保存のみ／変更＋メッセージ送信）で確定する
- **Googleフォームからの自動反映**：フォームの質問の1つに「管理番号」を用意し、フォームの回答先を
  このスプレッドシートに設定した上で、スクリプトエディタから `setupConsentFormTrigger` を1回実行すると、
  以後はフォーム回答時に自動で「同意書」欄が「済」になります（詳しい手順はCode.gs内のコメントを参照）。
  管理番号の入力ミスなどで自動反映できなかった場合は、画面から手動でチェックしてください。

### 40. セール名（プランとは別の入力欄）
セールは頻度が高く、名称もその都度変わります。プランマスタのように固定候補だけでは運用しづらいため、
プラン名とは別に **「セール名」** の入力欄を設けました。撮影希望場所と同じ運用で、事前にセールマスタへ
登録した候補から選ぶことも、その場で自由入力することもできます（支店により日本側だけが独自に割引・
特典を付けるケースもあるため、必須の選択式にはしていません）。

支店マスタの「ロール」列には `JP` / `BRANCH` のほか、店舗ロールの `SHOP` も指定できます（48.参照）。
`SHOP` の行は「支店コード」をログインID、「支店名」を店舗名、「ログインパスコード」「通知先メール」「有効」を
他のロールと同じ意味で使います（国・都市・手配チーム・案件番号プレフィックス等は使いません）。

### 42. セキュリティと堅牢性の強化（全API横断の監査を追加）
全APIを総当たりで検証する監査テスト（`test/audit_test.js`）を追加し、そこで見つかった弱点を
まとめて塞ぎました。

- **ログインの総当たり対策**：パスコードは短い合言葉のため、機械的に試されると破られ得ます。
  支店コード単位で連続失敗を数え、**10回**を超えると**15分間**その支店のログインを停止します
  （時間経過で自動解除。他の支店は巻き添えになりません）。
- **日付は認識できないなら保存しない**：以前は解析に失敗した日付を文字列のまま保存していたため、
  画面上は日付が入って見えるのに、**アラートも過去一覧への移動も当日表も一切効かない案件**が
  静かに生まれる状態でした。受け付けられない形式はその場でエラーにします
  （空欄にして日付を消す操作は従来どおり可能です）。
- **外部サイトへのiframe埋め込みを禁止**：`XFrameOptionsMode.ALLOWALL` をやめ、既定に戻しました
  （画面の上に透明な要素を重ねて誤操作させる手口への対策）。通常の利用に影響はありません。
- **異常入力で内部エラーを画面に出さない**：1,265通りの異常な入力を全APIへ流し込み、
  英語の内部エラーがそのまま利用者に見えないことを確認しています。

あわせて、以下が自動テストで保証されるようになりました（新しいAPIを追加して保護を
書き忘れると、テストが落ちて気づけます）。

- 公開API以外は必ず認証を通す／日本側専用APIは必ずJP判定を通す
- 案件を指定するAPIは必ず可視性チェックを通す／書き込みAPIは必ず排他ロックを取る
- セッション（未指定・偽造・期限切れ・ログアウト後）を全APIが拒否する
- ロック競合時に分かりやすく失敗し、ロックを保持したままにしない
- 保存は原子的（1項目でも不正なら何も書き込まない）
- 日本側と支店が同時に編集しても、互いの変更を消し合わない

### 43. 日本記入欄（日本側のみ表示、旧「社内進行管理欄」）
日本の手配課側だけが使う項目を、案件詳細の独立したタブ「日本記入欄」にまとめました
（旧称「社内進行管理欄」。47.のタブ再編成にあわせて名称・置き場所を変更しています）。
**支店側にはタブ自体が表示されず、値もサーバーから一切送られません**（画面を作り込むだけでなく、
`apiGetReservationDetail` のレスポンス自体から除外しています）。

| 項目 | 種別 | 備考 |
|---|---|---|
| 管轄 | 関東／関西の選択式 | 通常の3択（保存のみ等）で確定。支店側にも値は見えるが編集はできない |
| フォトブリッジ登録 | 済／未のチェックボックス | チェックした担当者名と日時（分単位）を自動記録（ベースは未） |

| データアップロード | 済／未のチェックボックス | チェックした担当者名と日時（分単位）を自動記録（ベースは未） |

影響するため、値そのものは支店にも見えますが、編集用の入力欄は支店側の画面には出ません。

### 48. 店舗発の新規依頼（新しい利用者区分「店舗」の追加）

日本の店舗スタッフがウェブアプリから直接、新規の撮影依頼を起票できるようにしました。
支店・日本の手配課とは別の第三のロール「店舗（SHOP）」を追加し、支店マスタに `ロール=SHOP` の行を
1店舗につき1行登録すると、その店舗専用のログインができます（ログイン画面の選択肢にも自動で出ます）。

**依頼の流れ**

1. 店舗としてログインすると、通常の一覧系メニュー（検索・当日表・納品待ち・設定・従来の「＋新規案件」＝
   貼り付け解析）は表示されず、代わりに「＋新規依頼」だけが使えます。
2. 「新規依頼」画面で、依頼先の支店（＝都市。プルダウンには国・都市も表示）、該当の手配課（関東／関西）、
   お客様名、希望日、プラン（支店ごとのプランマスタの候補から選ぶか自由入力）を入力して送信します。
3. 送信すると新規案件として作成され（採番も対象支店のプレフィックスに従います）、**日本の該当手配課と
   現地支店の両方に通知メールが届きます**。ステータスはSTS JP＝RQ、STS 支店＝NCで始まり、以降の流れは
   通常の案件と同じです。
4. 店舗の案件一覧には、自分が起票した依頼だけが表示されます（他の支店・他の店舗の案件は一切見えません）。
   案件を開くと、依頼状況（ステータス・希望日・プランなど）の確認と、メッセージのやり取りだけができる
   簡易な画面になります（項目の編集はできません）。

**やり取りの中継（既定：手配課が仲介）**

既定では、店舗↔支店のメッセージは直接つながっておらず、日本の手配課が仲介します。

- 店舗が送ったメッセージは、日本の手配課へ届きます（要対応表示・通知メールとも従来の「支店→JP」と同じ扱い）。
- 支店からの回答は、まず日本の手配課に届きます（現状の支店↔JPのやり取りと変わりません）。
- **手配課が現地の回答を店舗へ伝える**には、案件詳細の「メッセージ」タブに出る「宛先」で「店舗へ」を
  選んでから送信します（未選択の場合は今までどおり支店へ届きます）。この中継の操作以外、店舗と支店の
  メッセージは互いに見えません（支店には店舗↔JPのやり取りが、店舗には支店↔JPのやり取りが、それぞれ
  表示されないようにしています）。日本側（JP）だけは、監督のため両方のやり取りを常に閲覧できます。

**直結モード（支店マスタの「店舗直接やり取り許可」がON）**

「日本の手配課側が予めマスタで決める」という要件どおり、支店ごとに支店マスタの
「店舗直接やり取り許可」列（JPのみ編集可）をONにすると、その支店が関わる店舗発の案件では
**手配課を介さず、店舗と支店が直接メッセージをやり取り**します（店舗からのメッセージはそのまま支店へ、
支店からの回答はそのまま店舗へ届きます）。日本側は従来どおり全てのやり取りを閲覧できますが、
仲介の操作は不要になります。

**裏側の実装**

- 支店マスタに列を追加：`店舗直接やり取り許可`（BRANCHロールの行のみ意味を持つ）
- 予約一覧に列を追加：`起票元店舗`（店舗が起票した案件かどうか。空欄なら従来どおりの案件）、
  `未読 店舗`（店舗側の「要対応」フラグ、JP・支店と同じ仕組み）
- やり取り履歴に列を追加：`宛先ロール`・`起票元店舗`（誰が誰に宛てたメッセージかを記録し、
  店舗が絡む案件で「支店には店舗↔JPを見せない／店舗には支店↔JPを見せない」を実現するため）、
  `CHECK 店舗`・`DATE 店舗`・`CHECK 店舗 氏名`（店舗側の既読管理。画面はメッセージを開くと
  自動で既読にする簡易な作りで、JP／支店のような個別チェックUIは設けていません）
- 新API：`apiShopCreateRequest`（店舗ロール専用の新規依頼作成）。既存の `apiCommitChanges` は
  店舗が絡む案件の宛先（支店／日本の手配課／店舗）を毎回自動判定するようになりましたが、
  起票元店舗が無い従来の案件では今までどおりJP⇔支店の2択のままで、挙動は変わりません。
- 店舗ロールは案件の項目（ステータス・プラン等）を一切変更できません（メッセージの送受信のみ）。
  現地スタッフ手配・日本記入欄・共有メモなど、店舗が使う想定の無い既存APIも全て店舗ロールを拒否します。

### 49. 案件一覧の表示形式「表」にSTSを表示

検索画面のSTS(JP側)／STS(支店側)による絞り込み（10.）自体は既に実装済みでしたが、

### 50. 店舗発注の拡張要望（新規依頼フォーム拡張・DC/PC/NC・通知トグル・請求先・
　　　必要書類チェックリスト・ドライブ連携・フォーム事前入力URL）

48.で追加した店舗（SHOP）ロールを、より本格的な発注元として使えるように拡張しました。
「WEDLINK支店ポータル 拡張要望リスト（店舗発注・その他機能追加）」の1〜12章にそれぞれ対応しています。

**① 店舗発の新規依頼フォームの拡張（2章）**

「新規依頼」画面の入力項目を大幅に増やしました。

- お客様名は「新郎名（ローマ字）」「新婦名（ローマ字）」の2項目に分離
- セール名・撮影希望場所（どちらもマスタの候補＋自由入力）、準備場所（イタリアの支店を選んだ時だけ
  ホテル／サロンの選択式で表示）
- 希望日は1件→最大5件（第一〜第五希望）
- オプション名を最大5件まで新規作成時から入力可能（ステータスは既存案件詳細と同じ仕様のまま、
  つまり作成直後は未使用でJP・支店が後から設定する運用は変わりません）
- パスポート番号（対象支店がパスポート必須の場合だけ入力欄が出ます。既存の表示条件をそのまま踏襲）
- 新規作成時のSTS(JP側)を **RQ（予約依頼）／CHK（空き確認のみ）** から店舗が選べるようにしました
  （以前は常にRQ固定でした）

**② 案件作成後の店舗による編集（3章）**

- **通常の項目変更（3-1）**：新郎名・新婦名・プラン・セール名・撮影希望場所・準備場所・希望日①〜⑤・
  パスポート番号・オプション名（5件）を、既存の3択（保存のみ／メッセージのみ送信／変更＋メッセージ
  送信）で編集できます。それ以外の項目（請求先・ホテル等の内部項目、STS 支店など）は今までどおり
  変更できません。
- **日付変更・プラン変更（3-2、新設のDC/PCステータス）**：店舗はSTS(JP側)を **DC（日付変更依頼）**／
  **PC（プラン・式場変更依頼）** に設定できます（画面では選択時に「チャージ規定は各自ご確認ください」の
  警告を表示）。現地支店は通常のSTS 支店の編集と同じ操作で **OK／UC** を選んで応答しますが、
  DC・PCに対する応答だけは特例として **STS(JP側)・STS(支店側)の両方に同時反映**されます
  （`STATUS_AUTO_CASCADE`の仕組みを利用）。OKなら案件は継続（最終的なFN確定は今までどおりJPが
  手動で行います。自動ではFNになりません）。UC（対応不可）の場合は、現地が店舗と直接リブッキングする
  想定で、手配課へは差し戻されません。この仕組みはオプション（OPn）のSTSには影響しません
  （オプションは今までどおり独立したSTSロックのままです）。DC/PCは店舗発・JP手配課発どちらの案件にも
  共通で使える仕様です。
- **ネームチェンジ（3-3）**：STSコード`NC`の意味を「依頼なし・状態リセット」から**「ネームチェンジ」**
  へ変更しました。店舗はRQ/OK/FNの状態からNCを設定でき、現地支店がNC→OKへ動かすことで対応完了と
  扱います。コード上の仕組み（STS 支店の編集許可条件）は変わっていません。旧来の「リセット」用途の
  データが残っていても実害はありません（要望書側で「使った記憶がない」と確認済みのため、移行処理は
  行っていません）。

**③ STS(JP側)の権限整理（4章）**

店舗が設定できるSTS(JP側)は、新規作成時のRQ/CHKに加えて、案件作成後は
**FN・CR・NC・DC・PCのみ**です（`SHOP_STATUS_TARGETS`）。FNへの変更はSTS(JP側)が
OKの状態からのみ可能です（それ以外のCR/NC/DC/PCには現在値による制限を設けていません。
JP自身のSTS(JP側)編集がもともと無条件であることと揃えています）。それ以外の変更は今までどおり
現地・手配課の役割分担のままです。

> ⚠️ 実装メモ：要望書のこの章の権限表は文面上「店舗直接やり取り許可がONの支店に関わる、店舗発の案件」
> に限定して書かれていますが、3章の実際の仕様説明はこの限定に言及していなかったため、
> 本実装ではSHOP_STATUS_TARGETS・SHOP_EDITABLE_FIELDSともに**直結モードのON/OFFに関わらず、
> 店舗発の案件全てに適用**しています。運用上どちらが正しいかは要確認です（限定が必要であれば、
> `validateFieldPermission_`のSHOP分岐に対象支店の`shopDirect`判定を1行足すだけで対応できます）。

**④ 手配課通知トグル（5章）**

支店マスタに新しい列 **`店舗依頼の手配課通知`** を追加しました（既定＝ON＝空欄でも通知する）。
直結モードの支店で「手配課には毎回通知しなくてよい」場合、この列にFALSEを入れると、
店舗発の新規依頼で**手配課宛の通知メールだけ**が送られなくなります。手配課側の一覧・案件の閲覧権限、
要対応（未読）表示は今までどおりで、メールが届かなくなるだけです。

**⑤ 請求先マスタ（6章）**

支店マスタに新しい列 **`請求先`** を追加しました。SHOPロールの行にだけ意味があり、その店舗の

店舗がヘアメイク画像・衣裳画像・撮影指示書・着付け指示書をアップロードできるようにしました。

- 案件のアップロード欄を初めて使った時点で、自動でフォルダを作成します（フォルダ名は

- ⚠️ **要望書自身が明記している未検証事項（8-4）**：このWebアプリは

  アプリの実行方式を「自分（作成者）として実行」に変更するかの検討が必要になります。

案件詳細に「必要書類チェックリスト」を追加しました（ヘアメイク画像／衣裳画像／撮影指示書／

**⑨ 同意書・アンケートフォームの事前入力済みURL（10章）**

これまではお客様がGoogleフォームの「管理番号」欄に自分で入力する必要があり、実運用では
機能していませんでした。Googleフォームの「事前入力したリンク」機能を使い、管理番号を

有効にするには、管理者が最初に1回だけ設定が必要です（同意書・アンケートフォームそれぞれで実施）。

1. 対象のGoogleフォームを開く → 右上の「⋮」→「事前入力したリンクを取得」
2. 「管理番号」欄に何かダミー値（例：`TEST123`）を入力して「リンクを取得」
3. 表示されたURLの `entry.123456789=TEST123` のような部分から `entry.123456789`

4. URLの`entry.`より前の部分（`https://docs.google.com/forms/d/e/.../viewform`まで）を

要望書自身が「未確定」としている以下の点は、今回はいったん現状の実装のまま進めています。

  （双方向で見えることだけを実装）。
- 旧NC（依頼なし・状態リセット）の既存データについては、要望書側で「使った記憶がない」と

**まとめ：ステータスコード一覧**

### 51. 希望日ごとの空き確認ステータス・ステータス連動の不具合修正・チャレンジ番号入力欄

お客様からの追加要望・現場の運用に合わせた修正指示に対応しました。

**① 希望日ごとの空き確認ステータス（新設）**

これまでSTS(JP側)／STS(支店側)は案件全体で1組しか持てず、「第一希望はダメだったが第二希望が
取れた」というような希望日ごとの経過を記録できませんでした。オプション（OP1〜OP5）と同じ構造で、
**希望日①〜⑤それぞれにSTS(JP側)／STS(支店側)を新設**しました。

- 新規案件作成時、日付が入っている希望日だけ自動で **STS(JP側)=RQ／STS(支店側)=ST**
  （現地未確認）に初期化されます（第二希望までしか無い等、入っている分だけ）。
- 現地(支店)側がベンダー（カメラマン等）へ確認の連絡をしたら、その希望日のSTS(支店側)を
  **ST→RQ** に変更します（人が操作。連動はありません）。
- 取れたら **OK**、取れなければ **UC** に変更します（現地側が操作）。この回答は
  **同じ希望日のSTS(JP側)にも自動で反映されます**（DC/PCの回答と同じ「支店側の回答が
  JP側にも映る」例外パターン）。
- いずれかの希望日がOK/OKになると、自動で次の3つが起こります：
  1. **撮影日FIXにその希望日の日付が反映される**
  2. **他の入力済みの希望日が自動でUC/UCになる**（希望日は同時に1件しか確定しない前提）
  3. **案件全体のSTS(JP側)がまだ初期値RQのままなら、案件全体のSTS(JP側)・STS(支店側)も
     OKへ進める**（空き確認のみ＝CHKで作成した案件や、既にDC/PC/CR/NC等へ手動で
     進めている案件は巻き戻しません）
- どの変更も「誰が・いつ変更したか」が案件タイムラインに記録されます。
- 希望日ごとのSTS(JP側)は自動連動専用のシステム項目として扱い、直接編集はできません
  （人が直接編集するのはSTS(支店側)だけです）。
- 画面の「希望日から確定する」ワンタップボタンは、この新しい仕組みへ統合しました
  （押すとその希望日のSTS(支店側)がOKになり、あとは上記の自動連動に任せます）。

**② ステータス連動の不具合修正（3件）**

現場からの指摘で、以下の3つの反映漏れが見つかったため修正しました。

- STS(支店側)の初期値に、今はネームチェンジ専用のコードである「NC」を流用していたため、
  名前を変える予定の無い新規案件でも最初から「NC」と表示されてしまっていました。今は空欄です。
- キャンセルチャージが発生する **CF** の応答（現地→支店側）が、案件全体のSTS(JP側)へ
  反映されていませんでした（チャージ無しの**CW**だけ反映される片手落ちでした）。今は
  CFも同様にJP側へ反映されます。
- **ネームチェンジ完了時**、現地側の「OK」応答（＝名前変更対応完了）が、案件全体の
  STS(JP側)へ反映されていませんでした。今は反映されます（現地がOKにすると、JP側もOKになります）。
- STS(JP側)が **FN（最終確定）** になった後、現地側が自分のSTS(支店側)をFNにしようとすると
  編集ロックされて変更できない不具合がありました（`BRANCH_EDIT_GATE`に`FN`のキーが
  無かったため）。今は現地側もFNに変更できます。

**③ チャレンジ番号の入力欄（店舗発の新規依頼）**

店舗発の新規依頼フォームに「チャレンジ番号」の入力欄が無かったため追加しました（任意入力）。

**④ 送信後の案内**

店舗ロールが新規依頼・メッセージ・変更を送信した後、「ご回答まで今しばらくお待ちください。」の

### 57. チャレンジ番号の必須化・プラン/セール名/オプションのマスタ選択式・STS変更にRQを追加

店舗発の新規依頼まわりで、以下の3点を対応しました。

**(1) チャレンジ番号を必須・英数字11桁に**

これまでチャレンジ番号は任意入力（未入力なら「NoCH」として扱う）でしたが、実運用では
必ず割り振られる番号のため、新規依頼の作成時は必須・英数字ちょうど11桁（先頭が数字の
場合も、`0`から始まる場合も、アルファベットから始まる場合もすべて許可）でのバリデーション
を追加しました。入力欄のラベルにも「（必須・英数字11桁）」と明記し、例として
「0A2B3C4D5E6」のようにハイフンなしの11桁であることが分かるプレースホルダーを表示します。

- サーバー側：`CHALLENGE_NO_PATTERN = /^[A-Za-z0-9]{11}$/`（Code.gs）を新設。
  `apiShopCreateRequest`で未入力・形式不正の両方をエラーにする。既存案件の更新
  （`apiCommitChanges`経由）でも`validateFieldPermission_`側で形式チェックのみ
  行う（空欄のまま・元から入っている値まで巻き込んで必須化はしない）
- クライアント側：新規依頼フォームの送信前チェック（`submitShopNewRequest`）にも
  同じ正規表現でのチェックを追加し、サーバーへ送る前に分かりやすいエラーメッセージを表示

### 58. 店舗画面のクイックナビでスクロール先が固定ヘッダーに隠れる不具合を修正

第55回で追加したクイックナビ（タブを押すと該当セクションへスクロール）で、対象セクションが
短い場合（例：「お客様情報」＝氏名の入力欄4つだけ）に、画面上部に固定表示されている

  スクロール停止位置に固定ヘッダー＋クイックナビの高さぶんの余白を確保するよう修正

### 60. 一覧の「撮影日未定」表示をSTSに応じた文言に修正

案件一覧（カード表示・表表示どちらも）で、撮影日FIXが未入力の案件は一律「撮影日未定」と
表示していましたが、STS(JP側)・STS(支店側)がどちらもOKなのに「撮影日未定」と出るのは
おかしい、との指摘に対応しました。

撮影日FIXが入力されていれば今までどおりその日付を表示します。**未入力の場合だけ**、
STS(JP側)・STS(支店側)のどちらかに該当するコードがあれば、以下の文言に置き換えます
（該当が無い場合、例えばCHK・UC・DC・PCなどは、従来どおり「撮影日未定」のままです）。

| 条件（日本または現地のいずれかが） | 表示文言 |
| --- | --- |
| RQ | リクエスト中 |
| OK | 予約確定 |
| FN | 最終確定 |
| CR | キャンセル中 |
| CW | キャンセル済 |

上から順にチェックし、最初に一致したものを使います（例：日本がRQ・現地がOKの場合、
現地がまだ日本の正式なOK待ちの状態と見なして「リクエスト中」を優先します）。

- `caseStatusLabel_`（JavaScript.html）という共通関数を新設し、案件一覧のカード表示・
  表表示・検索結果のカードで使う`r.confirmedDate || '撮影日未定'`をすべて
  `r.confirmedDate || caseStatusLabel_(r.statusJp, r.statusBranch)`に置き換えました。
- 納品待ち・請求不備チェックの一覧（撮影後の案件を対象とする画面のため、撮影日FIXは
  通常すでに入っている想定）は対象外のままにしています。

### 61. 一覧の日付欄：文言と撮影日FIXを両方併記・UC/CHK/DC/PCの文言を追加

第60回の続きです。撮影日FIXが入っている案件は日付だけ、未入力の案件は文言だけ、と

### 62. オプションのSTS(JP側)を新規申し込み時以外でも常時変更可能に・OK後はCR/FNのみに制限

**① オプションのSTS変更欄を常に表示**

店舗の案件詳細画面で、オプション名が未設定（未使用の枠）の間はSTS(JP側)・STS(支店側)の
欄自体が表示されない仕様でしたが、新規申し込み時に限らずいつでもオプションの状況を

（日本側・支店側の画面はもともとこの制限がなく、今回店舗側もそれに揃えた形です）。

**② 一度OK（現地確定）になったオプションは、店舗からRQ・DC・PCへ戻せない**

これまでは店舗が設定できるSTS(JP側)（RQ/FN/CR/DC/PC）に現在値による制限が
ほとんどありませんでしたが（FNだけがOKからの遷移限定）、オプションが一度
**OK（現地確定）**になった後は、店舗が選べる値を**CR（キャンセル依頼）・FN（最終確定）の

> （日程変更・プラン変更の依頼は案件全体に対して行うのが元々の想定のため）。

- `validateFieldPermission_`（Code.gs）のSHOP分岐で、フィールドがオプション
  （`/^OP\d+ STS JP$/`）かつ現在値がOKの場合だけ、許可リストを
  `SHOP_STATUS_TARGETS_FROM_OK`に絞り込むよう変更
- `shopStatusCell`（JavaScript.html）も同じ条件でプルダウンの選択肢を絞り込む
  （サーバー側の制限と一致させ、選べない値がそもそも見えないようにする）

### 64. 現地支店・手配課の案件詳細を日本の店舗画面と同じ「常時スクロール＋クイックナビ」形式に統一

### 75. スプレッドシートIDを設定・setup系の関数がUIコンテキスト無しで失敗する不具合を修正

実際にデプロイ先のスプレッドシートIDを`SPREADSHEET_ID`（`Code.gs`冒頭）に設定した。あわせて、
Apps Scriptエディタから`setupPortal()`を手動実行したところ次の例外が発生する不具合が見つかり、
修正した。

```
[rebuildUnreadFlags] 0 行の未読フラグを再計算しました
Exception: Cannot call SpreadsheetApp.getUi() from this context.
  setupPortal @ Code.gs:738
```

- **原因**：`SpreadsheetApp.getUi()`は、スプレッドシートのカスタムメニューやサイドバー等、
  実際にスプレッドシートのUIから呼ばれた場合にしか使えない。`setupPortal`・`setupTriggers`・
  `setupConsentFormTrigger`・`setupSurveyFormTrigger`はいずれも本SETUP.mdの手順どおり
  Apps Scriptエディタの「実行」ボタンから直接手動実行する運用のため、UIコンテキストが無く、
  完了メッセージを`SpreadsheetApp.getUi().alert(...)`で出そうとした最後の行が必ず例外になって
  いた（シート作成・マスタのシード・未読フラグ再計算などそれ以前の処理は正常に完了していたが、
  最後の完了通知だけが失敗し、実行ログ上はエラー終了に見えてしまっていた）
- **修正**：4箇所の`SpreadsheetApp.getUi().alert(...)`を、共通ヘルパー`alertOrLog_(message)`
  経由に置き換えた。`alertOrLog_`はまず`console.log`で実行ログに必ずメッセージを残し、

**③ 新規予約作成後、一覧に戻っても何も表示されない不具合の調査**

「日本の店舗から新規で予約依頼したが、一覧に戻ると何も出てこない」という報告を受け、
サーバー側（`apiGetDashboard`・`rowInScope_`・`apiShopCreateRequest`）を作成直後の
一覧取得まで含めて再現テストしたが、この一連の流れ自体に不具合は見つからなかった
（店舗が起票した案件は`起票元店舗（COL_ORIGIN_SHOP）`で正しくスコープされ、一覧取得も
毎回サーバーへ問い合わせている＝画面遷移時にキャッシュを使い回して古い状態を表示する、
といった経路も無かった）。特定の状況（通信エラー・実行時例外など）が起きた場合に、
**エラーが数秒で消えるトースト通知だけで、一覧欄自体には何のヒントも残らず「何も
起きていないように見える」**ことが、体感として「何も出てこない」に繋がった可能性が高いと
判断し、`loadDashboard()`の失敗時に ①devtoolsで追えるよう`console.error`を残す
②一覧欄にも「一覧の読み込みに失敗しました。もう一度お試しください。」という消えない案内を
出す、という改善を行った。再発した場合は、この案内文言や開発者ツールのコンソールから
原因を特定できるようにしてある。

**④ 新規依頼の送信中に画面全体を覆うロード表示を追加**

①の対応（ボタンの文言変化・無効化）だけでは気づかれず「できたか分からず何度も押してしまう」
という報告への対応。`#loading-overlay`（白背景＋スピナー＋案内文）という画面全体を覆う
オーバーレイを新設し、`showLoadingOverlay_(text)`/`hideLoadingOverlay_()`で表示・非表示を
切り替える。まずは新規依頼フォームの送信中（`submitShopNewRequest`）に適用した。

**⑤ 読み込みに時間がかかる点について**

具体的にどの操作が遅いか特定できる情報が無く、今回は挙動を変えるような対応はしていない
（GAS＋スプレッドシートの構成上、書き込みが増える処理＝複数支店にまたがる新規依頼などは
元々やや時間がかかりやすい）。④のロード表示により、少なくとも「待っている」ことは
分かるようにしてある。体感が悪いままなら、次にどの画面・操作が遅いかを教えてもらえれば
個別に調査する。

**⑥ 別のプランに切り替えたときに前のプランの撮影地が残る不具合の修正**

②の作り直しにより、支店切り替え（旧`onShopNewBranchChange`）と希望日①プラン変更
（旧`onShopNewHopePlan1Change`）が別々の非同期処理として存在し、応答が前後すると
古い支店・古いプランの候補が後から表示に残ってしまうことがあった。1つの関数に統合し、
呼び出しごとに増える`shopNewPlan1ChangeToken`で「後から呼ばれた処理より前の応答は
反映しない」ようにしたことで、この種の食い違いが起きない作りにした。

**⑦ 送信後の完了案内の配色を白背景＋青文字に変更**

`.success-banner`（送信後の「予約依頼をしました」案内）の配色が緑背景・緑文字
（`background:#ecfdf5; color:#065f46`）で「暗くて見づらい」という指摘を受け、背景を白、
文字色を他の案内文言と同じ青（`--color-primary-dark`）に変更した（チェックのアイコン・枠線は
控えめに元の成功色を残している）。

**⑧ 通知メールにデプロイ後のURLを記載・希望日ごとの全プランを記載**

`sendDirectionalMail_`のメール本文末尾「ポータルで確認する」の行が
`(Webアプリのデプロイ後のURLをここに記載してください)`というプレースホルダのままだったため、
新しい定数`WEBAPP_URL`にユーザーから共有された実際のデプロイURLを設定し、本文に使うようにした。
再デプロイでURLが変わった場合はCode.gs冒頭の`WEBAPP_URL`を書き換える。

また、店舗発新規依頼の通知メールで「希望日：第一希望　フィレンツェフォト10/9　第二希望
ローマフォト10/11...」のように希望日ごとに異なるプランを選んでいても、**メール本文には

### 83. 新規依頼フォームのセール名・準備場所も希望日ごとに独立した欄に

「希望日、プランの下に、セール選択（撮影場所の上に）がそれぞれ出るようにして。あと準備場所も
ローマのみしか選択できないから、ローマの場合だけそのすぐ下に出るようにしてほしい」という
指摘への対応。項目81・82で希望日①のプラン欄の下に「撮影希望場所」だけが希望日ごとに
出るようにしていたが、「セール名」「準備場所」は依然として案件全体で1つずつの単独欄
（フォーム冒頭・希望日①より前）のままだった。

セール名・準備場所も、希望日①〜⑤それぞれのプラン欄の直下（撮影希望場所のすぐ上）に
移動し、各希望日が独立して持つ欄にした：

- **並び順**：希望日（第n希望）→ セール名（第n希望）→ 準備場所（第n希望・イタリアの支店の
  プランを選んだ場合だけ表示）→ 撮影希望場所（第n希望）。
- **セール名**：その希望日で選んだプランの提供元支店のマスタから、対象プラン一致（または
  全プラン共通）のものだけを候補にする（希望日①でこれまでやっていたのと同じ絞り込みを
  希望日ごとに行う）。
- **準備場所**：その希望日で選んだプランの提供元支店がイタリアの場合だけ表示する
  （選択肢自体はPREP_CHOICES固定で支店に依存しない）。

クライアント側は、支店切り替え・プラン変更のたびに走っていた`onShopNewHopePlan1Change`を、
希望順位nを引数に取る`onShopNewHopePlanNChange_(n)`に一本化した（希望日①だけは、これに
加えて依頼全体の基準支店の決定・AM/PM表示・オプション候補の取得も行う）。支店コードごとに
セール一覧・撮影希望場所候補をまとめて取得・キャッシュする`shopNewFetchBranchData_`を新設し、
複数の希望日が同じ支店になった場合の二重取得を防いだ（取得中のPromise自体をキャッシュする
ことで、同時に複数の希望日が同じ支店を選んだ場合の競合も防いでいる）。

サーバー側（`apiShopCreateRequest`）は、希望日ごとの`hopeSale{n}`・`hopePrep{n}`を受け取り、
希望日②〜⑤にも`希望日{n}場所`と同じ考え方で保存できるようにした。あわせて、これまで
「案件全体のセール名・撮影希望場所・準備場所」（`saleName`/`location`/`prep`）を支店ごとに
分割された**全ての案件へ無条件でコピーしていた**（自分に属さない希望日の入力内容が紛れ込む
ことがあった）不具合も、プラン名（`groupPlan`）と同じ考え方で「その案件に属する希望日の中に
値がある最初のもの」だけを反映するように修正した（`groupSale`/`groupLocation`/`groupPrep`）。

テスト: `node run_all.js`で1383件全て成功（サーバー756・監査171・画面456）

### 85. マーレ支店など「英語しか読めない支店」への対応（表示言語・支店メール通知）

**要件**：マーレ支店だけ特殊対応が必要。①英語しか読めないため、日本側からの連絡（メッセージ
本文・通知メール本文）は自動で英語に翻訳する。②画面表示も全て英語にする。③メールの通知は
現地支店側には不要（ただし今後必要になった時にすぐON/OFFを切り替えられるようにしておく）。
④日本側（JP・SHOP）の表示・通知は一切変更しない。

特定の支店名をコードに埋め込むのではなく、支店マスタに汎用的な設定列を2つ追加し、
**今後どの支店にも同じ設定で適用できる**形にした（マーレ支店はその1つ目の適用例）。

- `表示言語`（`BM_COL_DISPLAY_LANG`）：空欄／`ja` = 日本語（既定）、`en` = 英語。
  BRANCHロールの行のみ意味を持つ（`normalizeDisplayLang_`で正規化）。
- `支店メール通知`（`BM_COL_BRANCH_MAIL_NOTIFY`）：既定ON。既存の「新規依頼の支店通知」
  （新規依頼作成時の通知だけを止める設定）とは異なり、この列は**支店宛のメール通知全般**
  （新規案件・メッセージ・キャンセル成立・納品データ変更・納品期限アラート・未返信督促の
  ダイジェストまで含む）を一括で止める。案件の可視性・未読フラグには影響しない。

#### メール通知の一括制御

支店宛メールの宛先解決は`getBranchEmail_(branchCode)`という1つの関数を必ず経由している
（`sendDirectionalMail_`・納品期限アラート・未返信督促のいずれも）。ここに「支店メール通知」
がOFFなら空文字を返すロジックを追加するだけで、支店宛の通知経路すべてに一括で適用された。

#### 自動翻訳（LanguageApp）

`translateJaToEn_(text)`を新設。GAS標準の`LanguageApp.translate(text, 'ja', 'en')`を使い、
同じ文字列を何度も翻訳し直さないようスクリプトキャッシュ（文字列のMD5ハッシュをキーにする。
`Utilities.computeDigest`を使用）で結果を再利用する。翻訳サービスが失敗しても例外を投げず
原文を返し、表示・送信自体は止めない。

- **メール本文**：`sendDirectionalMail_`・納品期限アラート・未返信督促のいずれも、宛先に
  支店と日本側（JP/SHOP）の両方が含まれる場合は、支店の表示言語が`en`なら**支店だけ別メール・
  英訳した件名/本文で送る**（1通にまとめると宛先ごとに言語を変えられないため）。支店の
  表示言語が既定（日本語）のときは、従来どおり1通にまとめて送る挙動をそのまま維持する
  （既存の挙動・既存テストへの影響を避けるため、分割するのは英語支店が絡む場合だけ）。
- **画面表示**：`apiTranslateBatch(token, texts)`を新設。表示言語が`en`のBRANCHセッションの
  場合だけ実際に翻訳し、それ以外（日本語支店・JP・SHOP）は入力をそのまま返す。

#### 画面表示の自動翻訳（クライアント側）

当初は「固定のUIラベルは人手で正確な英訳をコードに用意する」方針で検討したが、画面内に
日本語文言が1,200箇所以上あることが分かり、実装量・作業回数の見合いから方針転換した：
**画面に表示された日本語テキストを、その場でLanguageApp（`apiTranslateBatch`経由）に投げて
英訳し、DOMへ書き戻す**方式にした（固定のUIラベルも、日本側が書いた自由記述＝メッセージ・
備考等も区別しない）。既存の画面コード（JavaScript.html・Index.html）には一切手を入れず、
`JavaScript.html`末尾に追加した自動翻訳の仕組み（`startAutoTranslateIfNeeded_`）だけで完結する：

- `#app`配下をMutationObserverで監視し、テキストノードの追加・変更と、
  `placeholder`/`title`/`aria-label`属性の変更を検知する。
- 検知した内容は即時ではなく80msだけデバウンスしてまとめ、`apiTranslateBatch`へ1回で
  まとめて送る（一覧など大量のDOMが一度に追加される画面で、通信回数・応答待ちの両方の
  負荷を抑えるため）。
- 日本語（ひらがな・カタカナ・漢字）を含まないテキストは翻訳APIを呼ばない。
- 対象はログイン中セッションが「BRANCHロールかつ表示言語=en」の場合だけ。判定は
  `apiLogin`がセッションに埋め込む`session.displayLang`で行う（JP・SHOPは常に`ja`）。
- ログアウト時に監視を止める（`stopAutoTranslate_`）。

**不具合修正（実装中に発見）**：翻訳結果に元の日本語がそのまま残る場合がある（固有名詞・
記号混じりの文字列など、翻訳が一部しか効かないケース）。テキストノードには「直前に自分が
書き込んだ値と同じなら再翻訳しない」というループ防止チェックがあったが、**属性
（placeholder等）にはこのチェックが抜けており**、同じ属性に何度も英訳を継ぎ足してしまう
不具合があった（`EN:EN:EN:...`のように際限なく伸びる）。属性ごとに直近の書き込み値を
覚える`i18nLastWrittenAttr`を追加して修正した。

**制限事項**：一度英語化されたDOM要素（Index.htmlの静的な見出し・ボタン等）は、同じブラウザ
セッション内で別の（日本語の）支店へログインし直しても、自動的には元の日本語に戻らない
（画面を再読み込みすれば直る）。実運用では1つの支店担当者が自分の支店としてログインし
続けるため、通常は問題にならない想定。

テスト: `gas_test.js`にセクション65〜67、`ui_test.js`にU51を追加。

### 86. 【不具合修正】項目85の総点検で見つかった4件

項目85を実装したあと、完成品を通しで点検し直したところ、次の4件が見つかったので修正した。

#### ① 手配メールの返信先が消えていた（実害あり）

`apiSendArrangementRequest`（現地スタッフ手配メール）は、外部の手配先（カメラマン・ヘアメイク等）へ
送るメールの**返信先（replyTo）**に支店のアドレスを入れている。ここが `getBranchEmail_` を使って
いたため、「支店メール通知」をOFFにした支店（＝マーレ支店）では**返信先が空になり、手配先からの
返信が支店に届かなくなっていた**。これは「支店へ通知を送るか」ではなく「支店の連絡先は何か」を
引く用途なので、通知設定に左右されない `branchContactEmail_` を新設して使い分けるようにした。

#### ② 手配課と支店が同じアドレスだと日本語のメールが消えていた

支店だけ英語で送るために「宛先の文字列から支店のアドレスを取り除く」方式にしていたため、
手配課と支店に同じアドレスが設定されている場合、取り除いた結果として**日本語版のメールが
1通も送られなくなっていた**（要件「日本側は通常通り」に反する）。アドレスの文字列比較ではなく
「宛先の役割（手配課／支店／店舗）」で判定する方式に変え、同じアドレスでも日本語版と英語版が
1通ずつ届くようにした。

#### ③ 入力欄（textarea）の中身まで英訳され、保存するとデータが壊れる恐れがあった（実害あり）

画面の自動翻訳はテキストノードを書き換えるため、`<textarea>`の中身——たとえば案件詳細の
「キャンセル理由」に日本側が書いた文章——まで英訳で置き換わっていた。この状態で支店側が

#### ① 「一覧に何も出ない」不具合の原因調査

  断定できない。

  気づくのではなく、重くなってきた兆候の段階で気づけるようにするため。
- **マスタのキャッシュ化**：案件詳細を開くたびに、支店に依存しない全社共通のマスタ

  大きく変わるものではないため、最初の1回だけ取得しセッション中は使い回すようにした

### 88. 【不具合修正】撮影希望場所の「案件全体用」と「希望日ごと」の欄の食い違い（項目87③の対応）

項目87③では「説明のみで実装は変更していない」としていたが、ユーザーに実際の画面（記入欄
タブの単独の「撮影希望場所」欄／予約内容タブの「希望日・プラン・オプション明細」表の
希望日ごとの「場所」欄）をスクリーンショットで示しながら原因を確認したところ、対応する方針
で合意したため実装した。

原因を`applyHopeStatusCascade_`（希望日のSTS(支店側)がOKになったときの自動連動処理）の中で
突き止めた。この処理はもともと、確定した希望日の「日付」と「プラン」は案件全体の欄（撮影日
FIX・プラン名）へ自動でコピーしていたが、**「場所」だけこの自動コピーの対象から漏れていた**
（実装時の見落としと考えられる。日付・プランと横並びの項目でありながら、場所だけ対応する
コードが無かった）。そのため、希望日ごとの場所欄を書き換えても、記入欄タブの単独欄（当日表
や通知メールが参照する）には反映されず、担当者が単独欄を手作業で書き直さない限り、当日表・
メールには古い（または空の）場所が表示され続けていた。

対応：日付・プランと全く同じ書き方で、「場所」も確定した希望日の値を案件全体の撮影希望場所欄
（`COL_LOCATION`）へ自動反映するようにした。挙動は日付・プランに合わせてあり、以下の性質を
そのまま踏襲している。
- 確定した希望日に場所の指定が無ければ、何も上書きしない（既存の値を空で潰さない）。
- 確定しなかった他の希望日の場所欄は変更しない。
- 新規作成時の自動コピー（希望日①の場所を初期値として使う、項目77で実装済み）はそのまま。
  今回の修正は「確定した"時点"でもう一度反映し直す」処理を追加しただけで、既存の新規作成時の
  挙動とは独立している。

これにより、単独欄と希望日ごとの欄が食い違ったまま残るのは「まだどの希望日も確定していない
（STS(支店側)がOKになっていない）段階で、担当者が希望日ごとの場所欄だけを書き換えた場合」に
限られるようになった（この段階では当日表・メールもまだ日付未確定のため実害は小さい）。

テスト：`gas_test.js`のセクション50（希望日ごとのプラン反映の既存テスト）に、場所についても
同様の確定時反映・非上書きの確認を追加。`node test/run_all.js`で1454件全て成功
（サーバー816・監査171・画面467）。

### 90. 管理番号を二度と再利用しない（採番台帳の新設）

「一度キャンセルした管理番号が復活して次の予約に使われるのか」という確認を受けて調べた結果と対応。

#### 調べて分かったこと

- キャンセル（CW）にしただけでは行は消えず、予約一覧に残り続ける。撮影日FIXを過ぎれば過去一覧へ
  移動する。採番は予約一覧と過去一覧の両方を見ていたため、**通常の運用では番号は再利用されない**。
- ただし**行そのものをスプレッドシートから人が削除した場合は、最大値が下がって番号が再利用される**
  状態だった。キャンセル案件を手作業で整理する運用は自然に起こりうるため、実害のある穴と判断した。
  この場合、過去のメール・PDF・請求書に書かれた管理番号が、別のお客様の案件を指すことになる。

#### 対応

採番台帳シート（`採番管理`。列は「支店コード」「最終採番番号」「最終更新日時」）を新設し、
`nextKanriNo_`が「予約一覧・過去一覧を数えた最大値」と「台帳に記録された最終採番番号」の
**大きい方**の次の番号を発行し、発行した番号を台帳へ書き戻すようにした。

### 92. 【機能追加】翻訳の用語集（英語支店向けの訳を固定する）

英語専用支店（マーレ支店）向けの表示・メールは、その場で機械翻訳している（項目85）。機械翻訳は
同じ言葉を毎回同じ訳にするとは限らないため、「同意書」「手配課」「撮影日FIX」のような業務用語が
ぶれると、支店側の担当者が同じものを別のものと受け取る恐れがある。決まった訳を当てる仕組みを追加した。

- 新しいシート **`用語集`**（列は「日本語」「英訳」「有効」）。マスタ管理画面から編集できる
  （JPのみ。全社共通の設定のため支店・店舗は閲覧も編集もできない）。
- 効き方は2段階：
  1. **文字列そのものが用語集にある場合**は、その訳をそのまま使う（機械翻訳を呼ばない）。
     画面のラベル・ボタン・見出しはこれで完全に固定できる。通信も1回減る。
  2. **文の中に用語が含まれる場合**は、その部分をいったん目印（`TERM1Z`のような英数字）に
     置き換えてから機械翻訳し、返ってきた文の目印を決まった訳へ戻す。
- **安全策**：目印が1つでも翻訳結果から消えていた場合は、置き換えを使わず、原文をそのまま
  機械翻訳した結果を採用する。翻訳エンジンが目印を壊した場合でも、意味の欠けた文や
  `TERM1Z`のような文字列が画面に出ることは無い。
- 英→日方向（項目87）でも、用語集の英訳と完全に一致する文字列は機械翻訳を呼ばずに日本語へ戻す。
- **翻訳結果のキャッシュのキーに用語集の版番号を混ぜている。** これが無いと、用語集を直しても
  最大6時間は古い訳が使われ続けてしまう。用語集を保存した時点から新しい訳が使われる。
- 用語集が空でも従来どおり動く（すべて機械翻訳）。既存の運用スプレッドシートでもシートは
  自動作成される。

テスト：`gas_test.js`にセクション75を追加（完全一致・文中の置き換え・目印が残らないこと・
無効な行を使わないこと・用語集変更が即反映されること・権限）。`audit_test.js`にも認可チェックを登録。
`node test/run_all.js`で1524件全て成功（サーバー848・監査177・画面499）。

### 99. 実運用で見つかった5点の不具合に対応

実際にデプロイして運用してみたユーザーから、スクリーンショット付きで5点の報告を受けて対応した。
いずれも推測だけで直さず、`test/gas_harness.js`を使って実際にシナリオを再現し、直る前後の挙動を
確認したうえで修正している。

**① 新宿店から申し込んで現地には届いているのに、新宿の一覧には出ない**

`apiShopCreateRequest`内の`setV`ヘルパーが、`headers.indexOf(name)`で列が見つからない場合に
**値を静かに無視する**作りだった。運用スプレッドシートの列構成が古く「起票元店舗」列が
無かったため、店舗が新規依頼を作っても支店コード等は問題なく書き込めて現地には正しく
届く一方、`起票元店舗`（`COL_ORIGIN_SHOP`）だけが保存されず、店舗自身の一覧の絞り込み
（`assertShopOwnRow_`・`rowInScope_`）で「自分が起票した案件」と認識できずに一覧から
消えて見える、という状態を実際に再現して確認した。`setV`を、**値があるのに列が無い場合は
分かりやすいエラーを投げる**よう修正（「スプレッドシートに「〇〇」列がありません。
setupPortalを一度実行してください」）。`apiCreateReservation`内の同名ヘルパーにも同じ修正を
入れた。あわせて、スプレッドシート上の支店コード等に前後の空白が混じっているとアクセス
権限チェックで弾かれる不具合も見つかったため（②とあわせて修正、下記参照）、この2つが重なると
「一覧には出ない」不具合として体感されやすい状況だった。

**② ローマ支店は入れるのに、ウィーン支店はログインはできても詳細の読み込みに失敗する**

案件一覧の絞り込み（`rowInScope_`）は支店コードを`.trim()`してから比較していたが、
詳細画面を開くときの権限チェック（`assertRowVisible_`・`assertShopOwnRow_`）には
`.trim()`が抜けていた。スプレッドシート上の支店コードに末尾スペース等の表記ゆれが
あると、**一覧には出るが、開こうとすると「この案件を閲覧・操作する権限がありません」に
なる**という、まさに報告どおりの状態になることを確認した。この2関数に`.trim()`を追加。
あわせて`grep`で洗い出したところ、`apiCheckStaffConflict`や支店マスタの逆引き
（`branchMetaMap_`使用箇所）など複数箇所に同様の`.trim()`漏れがあったため、まとめて修正した。

**③ 新規予約時、第一希望以外の撮影場所・セール名が表示されない／ローマ半日コースだけ出ない**

複数パターンで再現を試みた（単純な選択操作・連続した選択操作・通信の遅延を模したもの）が、
いずれも正常に動作し、決定的な原因は特定できなかった。実運用限りで起きている可能性が高い
（通信の遅延順序、ブラウザのキャッシュ、マスタ登録直後の反映タイミングなど）。原因を
断定できないため、次に同じ現象が起きたときに開発者ツールのコンソールから絞り込めるよう、
`onShopNewHopePlanNChange_`（希望日ごとのプラン選択時に撮影希望場所欄を描画する処理）の
堅牢性を強化した：撮影希望場所欄の描画を`try-catch`で局所化し、失敗してもキャッシュから
プラン情報を拾って処理を継続させ、選んだプランが候補一覧に見つからない場合は
`console.warn`で「プランマスタの登録内容を確認してください」と警告を残すようにした。
なお「ローマ半日コースのみ撮影場所・セール名が出ない」という個別の報告は、プランマスタの
登録内容（該当プランの撮影場所方式・候補設定）自体を確認する必要があるため、まずマスタ管理
画面でこのプランの設定内容を確認してもらうよう依頼した。

**④ 複数支店にまたがる依頼で、後ろの支店の希望日が空欄のまま変な位置に入る**

例：フィレンツェ①・ローマ②・ウィーン③・カッパドキア④、という依頼を出すと、日本側は
入力順どおりでよいが、**現地側（ウィーン）は第一・第二希望が空欄で第三希望にしかデータが
入らない**、**イスタンブールも第四希望にしかカッパドキアが入らない**という報告。
`test/`で同じ組み合わせを実際に再現したところ、報告どおりの状態を確認した。原因は
`apiShopCreateRequest`内の支店ごとの分割処理（`groups`構築）で、各支店グループの
`hopeIndexes`（元の希望順位のインデックス）をそのまま希望日①〜⑤の列に書き込んでいたため
だった（ウィーン分の希望日は元の並びで③番目なので、そのまま希望日③に書き込まれていた）。
**分割後の案件ではその支店内での相対順位に「詰め直して」書き込む**よう修正した
（`group.hopeIndexes.forEach((i, localIdx) => ...)`で、書き込み先の列を`localIdx`ベースに
変更）。通知メールの希望順位表記（「第◯希望」）も同じ考え方で詰め直し後の順位を使うよう
修正。この仕様変更に伴い、既存テスト3件（分割時の希望日の入り方・通知メールの希望順位表記）の
期待値も、詰め直し後の順位に合わせて更新した。

**⑤ 現地側が「希望日一覧」と「プラン・オプション明細」の両方のSTS(支店側)をいじれてしまう**

新規予約が来た際、現地は上の「希望日一覧」のSTS(支店側)と、下の「プラン・オプション明細」
（案件全体のプラン行）のSTS(支店側)の**両方**を編集できてしまい、どちらで回答すればよいか
分からない、という報告。要件を整理すると：

- 案件が未確定（STS JPがRQ／CHK）の間は、回答は「希望日一覧」からだけ行う
  （プラン行のSTS(支店側)は編集不可＝ロック表示にする）。
- 希望日一覧でOKになると、その内容（日付・プラン・場所）が下のプラン行にも自動反映され、
  希望日一覧はふだんアコーディオンで折りたたまれる（これは項目66の「撮影日FIX未確定または
  STS(JP側)がDCの間だけ自動で開く」という既存の仕組みがそのまま条件に合致するため、
  変更は不要だった）。
- OK確定後は、プラン行のSTS(支店側)を現地が編集できるようになる（例：日本からCR
  （キャンセル依頼中）が来たら、現地はプラン行のSTS(支店側)をCW（キャンセル成立）に
  する、という従来からの流れ）。
- 新しい日付でOKが取れても、既にOKになっている希望日を自動でキャンセル扱いにはしない
  （日本の支店から使わない方の日付にCRが来るまではそのまま）。これは
  `applyHopeStatusCascade_`の「他の入力済み希望日を自動でUC/UCにする」処理が、
  もともとOK／UC**以外**（未回答＝ST/RQ）の希望日だけを対象にしており、既にOK／UCの
  希望日には手を触れない作りだったため、**変更せずそのまま要件を満たしていた**。

上記の前半（未確定の間はプラン行を編集できないようにする）だけが実際のコード変更点。
案件全体のSTS(支店側)（プラン行）専用のゲート`BRANCH_MAIN_EDIT_GATE`を新設した：

```js
const BRANCH_MAIN_EDIT_GATE = {
  'CR': ['CW', 'CF'],
  'DC': ['OK', 'UC'],
  'PC': ['OK', 'UC'],
  'FN': ['FN']
};
```

既存の`BRANCH_EDIT_GATE`（希望日・オプションのSTS(支店側)に使う、`'RQ': null`
＝無制限で含む）とは別物にした。希望日には「希望日一覧」という代替の回答経路があるが、
オプションには無いため、**対象を案件全体のSTS(支店側)だけに限定**し、希望日・オプションの
ゲートには手を加えていない。`validateFieldPermission_`で`field === COL_STATUS_BRANCH`
（案件全体のSTS支店）のときだけ`BRANCH_MAIN_EDIT_GATE`を使うよう分岐した。RQ・CHKは
このオブジェクトにキー自体が無いため、未確定の間はプラン行のSTS(支店側)が完全にロックされる。

この変更により、**「STS(JP側)がRQのとき、支店が案件全体のSTS(支店側)を直接UCで回答すると
JP側も自動でUCになる」という旧仕様の自動連動（`STATUS_AUTO_CASCADE`）が、そもそも
到達不能になった**（この直接編集の経路自体がロックされたため）。到達不能になったルールは
`STATUS_AUTO_CASCADE`から削除し、希望日一覧経由の回答・連動（`applyHopeStatusCascade_`）が
唯一の回答経路であることをコメントで明記した。CR→CW/CF、DC/PC→OK/UCの既存の自動連動は
影響を受けず従来どおり動く。

**④の補足：詰め直しは「支店をまたぐ分割」以外でも働く**

希望日を飛ばして入力した場合（第一希望と第三希望だけ入れて第二希望は空欄、など）も、
同じ処理で前に詰めて保存される（上の例なら希望日①②に入り、③以降は空欄になる）。
現地から見たときに歯抜けの行が出ないほうが分かりやすいため、この挙動のままにしている。
入力を飛ばさず順に埋めた場合は、当然ながら入力どおりの順序で保存される（並びは変わらない）。

**⑤の実装後の総点検で見つけた1件（案内文言と実態の食い違い）**

⑤を実装したあと、「空き確認のみ（CHK）」の案件で通しの動作を確認したところ、
現地が希望日一覧で回答を済ませた後も、プラン行のロック理由が
「確定前は上の『希望日一覧』から回答してください」のまま出続けていた。
これは、CHKの案件は希望日に回答しても案件全体のSTS(JP側)がCHKのまま据え置かれる
（`applyHopeStatusCascade_`は初期値RQのときだけOKへ進める＝空き確認の依頼を勝手に予約確定に
しないための、従来からの正しい仕様）ことによるもので、**回答済みなのに「まだ回答していない」
ように読める案内**になっていた。⑤の目的が「どこで回答すればよいか分かるようにする」ことなので、
`mainStatusLockReason_`に判定を1つ足し、いずれかの希望日に回答（OK／UC）済みなら
「希望日一覧で回答済みです。日本側の確定をお待ちください」と案内を切り替えるようにした
（表示のみの変更で、保存内容・権限には影響しない）。
