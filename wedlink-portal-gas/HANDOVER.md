### ラウンド5（項目85）：リポジトリの引っ越し＋マーレ支店（英語専用支店）対応

このセッションの前半で、旧スレッドの成果物（項目1〜84まで）を現在のリポジトリへ移行した。
その後、ユーザーから「マーレ支店だけ特殊対応が必要。①英語しか読めないので日本からの
連絡は全て自動で英語に翻訳、②表示も全て英語、③メール通知は現地支店に不要（今後
ON/OFF切替できるように）、④日本側は通常通り」という要望を受け、以下を実装：

- 支店マスタに`表示言語`（`en`/既定`ja`）・`支店メール通知`（既定ON）の2列を追加。
  **マーレ支店に限定せず汎用的な設定**にしてあるので、他の支店にも同じ設定でそのまま使える。
- `getBranchEmail_`を経由するすべての支店宛メール通知を「支店メール通知」で一括制御。
- 日本側からの連絡（メッセージ本文・通知メール本文）はGAS標準の`LanguageApp`でその場で
  英訳。宛先にJP/SHOPと支店の両方が含まれる通知は、英語支店が絡む場合だけ支店宛を
  別メール・英訳して送る（日本語支店は従来どおり1通にまとめる挙動を維持）。
- 画面表示は、固定UIラベルを人手で英訳する方式ではなく（日本語文言が1,200箇所以上あり
  非現実的と判断）、**表示された日本語をその場でLanguageAppに投げて書き戻す**
  自動翻訳方式にした（MutationObserverでDOM監視。JavaScript.html末尾に追加、既存の
  画面コードは無改変）。実装の詳細・ハマりどころ（属性の再翻訳ループ防止漏れ等）は
  `CLAUDE.md`「多言語対応」章とSETUP.md項目85を参照。
- テスト：`gas_test.js`にセクション65〜69、`ui_test.js`にU51を追加。
  `run_all.js`で1440件全て成功（サーバー804・監査171・画面465）。
- **実装後に完成品を通しで再点検し、4件の不具合を発見・修正した（SETUP.md 項目86）。**
  特に重要な2件：①現地スタッフ手配メールの返信先が「支店メール通知OFF」で消えていた
  （手配先からの返信が支店に届かない）、②画面の自動翻訳が`<textarea>`の中身まで書き換えており、
  支店側が保存すると日本語データが英訳で上書きされる恐れがあった。
- モックアップ（PC用・スマホ用）にもマーレ支店のデモデータ・ログインショートカットを追加。
  `LanguageApp`・`Utilities.computeDigest`のモックを`gas_harness.js`・`mockup_core.js`
  それぞれに追加済み。

**次の担当者への申し送り**：実際のマーレ支店の行が運用スプレッドシート側に既に存在するか
未確認。存在する場合は、その行の「表示言語」列に`en`を、必要に応じて「支店メール通知」列に
`FALSE`を設定するだけで今回の機能が有効になる（コード変更は不要）。存在しない場合は、
支店マスタに新規追加が必要。

## 3. 新規依頼フォームの現在の構造（いちばん複雑なので詳述）

### 画面の並び順

```
案内（.multi-branch-note：複数支店にまたがる依頼も1回で送れます）
該当の手配課 / 新規作成時のSTS(JP側) / チャレンジ番号
新郎姓・名 / 新婦姓・名
┌ 帯：下記はFN確定までに要入力
├ 新郎年齢 / 新婦年齢
希望日（第一希望） [日付][AM/PM][プラン]      ← プランが基準支店を決める
  セール名                                    ← そのプラン用に絞り込み
  準備場所（ローマの場合は選択）              ← イタリアの支店のときだけ表示
  撮影希望場所                                ← プランごとに自由入力／プルダウン／チェックボックス
希望日（第二希望）〜（第五希望）も同じ4点セットを繰り返す
オプション①〜⑩（⑥〜⑩は折りたたみ）
備考 / 送信ボタン
```

### ID の付け方（重要）

希望日①だけは**後方互換のため旧IDのまま**、②〜⑤は連番付き。ヘルパー関数で出し分けている：

| 用途 | 希望日① | 希望日n（2〜5） | ヘルパー |
|---|---|---|---|
| プラン | `shop-new-hopeplan1` | `shop-new-hopeplan{n}` | （そのまま連番） |
| セール名 | `shop-new-sale` | `shop-new-hopesale{n}` | `shopNewHopeSaleId_(n)` |
| 準備場所（枠） | `shop-new-prep-block` | `shop-new-hopeprep-block{n}` | `shopNewHopePrepBlockId_(n)` |
| 準備場所（選択） | `shop-new-prep` | `shop-new-hopeprep{n}` | `shopNewHopePrepSelectId_(n)` |
| 撮影場所（入力） | `shop-new-location` | `shop-new-hopelocation{n}` | `shopNewHopeLocationInputId_(n)` |
| 撮影場所（枠） | `shop-new-location-wrap` | `shop-new-hopelocation-wrap{n}` | `shopNewHopeLocationWrapId_(n)` |
| 撮影場所（datalist） | `shop-new-location-datalist` | `shop-new-hopelocation-datalist{n}` | `shopNewHopeLocationDatalistId_(n)` |
| 撮影場所（チェック） | `.shop-new-location-cb` | `.shop-new-hopelocation-cb{n}` | `shopNewHopeLocationCbClass_(n)` |

**新しく希望日ごとの項目を足すときは、必ずこのヘルパー方式に合わせること。**

### クライアント側の処理の流れ

```
openShopNewView()
  ├ 各欄をリセット・準備場所の選択肢を5つ分用意
  ├ apiListAllActivePlans() で全支店横断のプラン一覧を1回だけ取得（shopNewAllPlansCache）
  └ onShopNewHopePlanNChange_(1〜5) を並列で初期化

onShopNewHopePlanNChange_(n)   ← 希望日nのプラン変更でも呼ばれる
  ├ トークン採番（shopNewHopeChangeTokens[n]。後着優先で古い応答を捨てる）
  ├ renderShopNewHopeLocation_(n)  … 撮影希望場所を即描画（通信不要）
  ├ 基準支店 branchCode = planMeta.branchCode
  │   └ n===1 のときだけ shopNewActiveBranch を更新＋AM/PM表示＋オプション候補を取得
  ├ 準備場所ブロックの表示切替（meta.country === 'イタリア' のときだけ表示）
  └ shopNewFetchBranchData_(branchCode) でセール一覧・撮影場所候補をまとめて取得
      （支店コードごとにPromiseごとキャッシュ。同じ支店の希望日が複数あっても1回しか取りに行かない）
```

### サーバー側（`apiShopCreateRequest`）

- `payload.branchCode` は**画面からはもう送られない**。無い場合は希望日①のプランから
  `planOwnerBranchMap_()` で逆引きする（明示的に渡された場合は優先＝テスト・外部呼び出しとの後方互換）
- 希望日ごとの値：`hopeTime{n}` / `hopePlan{n}` / `hopeLocation{n}` / `hopeSale{n}` / `hopePrep{n}`
  （**希望日①だけは従来どおり `location` / `saleName` / `prep` で送る**＝後方互換）
- 希望日ごとに提供元支店が違えば**案件を支店ごとに自動分割**して複数作成する
- 案件（グループ）ごとの値は `group.hopeIndexes` の中から値のある最初のものを採用：
  `groupPlan` / `groupSale` / `groupLocation` / `groupPrep`
  → **シートへの保存も、通知メール本文も、この値を使うこと**（項目84の不具合はここを間違えたもの）

## 4. 落とし穴・注意点（引き継ぐ人が踏みやすい順）

1. **`CLAUDE.md` を必ず読むこと。** 3ロールモデル・`BRANCH_EDIT_GATE`・`SHOP_STATUS_TARGETS` の
   3段階など、直感に反する仕様がまとまっている（特に `'OK'` が `BRANCH_EDIT_GATE` のキーに
   **無いのは意図的**。バグではない）。
2. **同じ分岐がCode.gsとJavaScript.htmlの両方にある箇所がある。** 店舗が設定できるSTSの許可値
   （`validateFieldPermission_` と `shopStatusCell`）。片方だけ直すと画面とサーバーがずれる。
3. **テストは機能を変えたら必ず追加する。** `test/gas_test.js` はセクション番号（現在64まで）、
   `test/ui_test.js` は `U○○`（現在U50まで）の連番で末尾に足していく形式。
4. **チャレンジ番号は英数字ちょうど11桁。** テストデータを書くとき12桁にしがち（何度もやった）。
5. **`ui_test.js` のフィクスチャは1つの `ctx` を全セクションで共有している。** 前のセクションで
   追加したマスタ行（例：U43でROW支店のプランを追加）が後のセクションでも効く。逆に、
   後のセクションで必要なマスタは**そのセクションより前で登録されているか**を確認すること。
6. **`gas_test.js` の `featureFixture()` にはローマ（イタリア）支店が無い**（KANTO/VIE/ISTのみ）。
   準備場所などイタリア限定の挙動をテストするときは `addBranchRow` で追加する。
7. **`mockup_core.js` の巨大テンプレートリテラルの中で `\n` を書かない。** 外側のエスケープが
   先に効いて本物の改行になり、埋め込み先のスクリプトが壊れる。区切りは全角読点 `、` を使う。
8. **モックアップの `dist/` は `.gitignore` 済み**（生成物）。渡す前に必ず再ビルド＋構文チェック＋
   Playwrightでの目視確認をすること（手順は `CLAUDE.md`）。
9. **スマホ用Artifactは同じURLを更新する。** `action:"publish"` に `url` を渡す。毎回新規作成すると
   別URLになってユーザーが混乱する。

3. `cd test && node run_all.js` で3種とも0件失敗にする

5. コミット（日本語の説明的メッセージ）→ `git push -u origin claude/global-system-rollout-sx537y`
