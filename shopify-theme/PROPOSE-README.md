# 世界のプロポーズプラン — Shopify実装ガイド（v2 再設計）

対象ユーザーを「旅行先・日程がすでに決まっていて、出発の5〜7日前にプロポーズを思い立った人」と
定義し直した再設計（v2）の、Shopify実装のための設計書です。

- **動くモックアップ（v2・完成）**: `/propose-lp/all-in-one.html`（1ファイル・オフライン可）
  ソースは `/propose-lp/src/`、ビルドは `python3 propose-lp/build.py`
- **Shopify用のLiquid（v2・実装済み）**: `layout/propose.liquid`・`sections/propose-*`・`snippets/propose-*`・`templates/`・`assets/propose*`
- **本番の設定手順**: `PROPOSE-SETUP.md`（管理画面での作業を順番に説明）

モックアップの `src/data.js` は、下記メタオブジェクトのフィールドと1対1で対応するように作ってあります。
Liquidへの移植は「名前の置き換え」で済み、構造の再設計は不要です（対応表は §6）。

## 1. 導線の考え方

```
Google / Instagram
  └→ /pages/propose/hawaii（ロケーション詳細・最重要ページ）  ← 直接着地する想定
       Hero（写真・料金 ¥128,000〜・「受付状況を見る」）
       └→ 同じページ内の「受付状況」で 9/28 17:30 OPEN を選ぶ
            └→ 予約フロー STEP 3/5（プラン・オプション）から開始 ← 日付・時間は入力済み
                 └→ お客様情報 → 確認 → 「予約をリクエストする」（この時点で支払いなし）
                      └→ 運営がフォトグラファーの手配を確認（24時間以内に返信・仮の値）
                           └→ 確定メール＋お支払いリンク → お支払い完了で予約確定
```

- **予約はリクエスト制**。フォトグラファーの手配をその場で確定できないため、画面では「予約が決まりました」
  とは言わず、「リクエストを受け付けました／まだ確定していません／○時間以内にご連絡」と表示します。
  お支払いは確定のあと。直前（5〜7日前）に申し込む人が多いので、返信までの時間は各所に明記します。

- ロケーション詳細から来た場合、予約フローは **旅行先の選択をスキップ**（5ステップ）。
  受付状況で日時を選んで来た場合は **日付・時間もスキップ**し、STEP 3 から始まります。
- TOP は「旅行先から探す」が主役。旅行先未定の人には、旅行先カードの上の「プロポーズしたい場所は？」タイルで絞り込ませる（景色タグ探しは廃止）。
- 計測するKPI（離脱を見る段階）: ロケーションページ到達 → 受付状況の操作 → 予約フロー開始 → リクエスト送信 → 確定・支払い完了。

## 2. URL構造

| URL | 内容 | Shopifyでの実現方法 |
|---|---|---|
| `/pages/propose` | TOP | 通常のページ（ハンドル `propose`）＋テンプレート `page.propose-home` |
| `/pages/propose/hawaii` など | ロケーション詳細 | **メタオブジェクトのWebページ機能**。定義 `propose` で「Webページとして公開」を有効にすると、エントリごとに `/pages/propose/<ハンドル>` のURLが付き、テンプレート `templates/metaobject/propose.json` で描画される |
| `/pages/propose-booking?loc=&date=&time=` | 予約フロー | 通常のページ＋テンプレート `page.propose-booking`（`layout/propose.liquid`・noindex） |

> 要確認：ハンドル `propose` の通常ページと、タイプ `propose` のメタオブジェクトWebページが
> 同じ `/pages/propose` 配下で競合しないかを開発ストアで確認してください。競合する場合は
> TOPのハンドルを `propose-top` にします（ロケーションURLは変わりません）。

メタオブジェクトのWebページにすることで、v1の「ページ＋メタフィールドで紐付け」が不要になり、
**ロケーション追加はメタオブジェクトを1件作るだけ**になります。

### 3.2 商品（プラン）

プランは **3段階＋オプション** です（どのプランにも花束が入ります）。

```
商品「ハワイ プロポーズプラン」（ロケーションごとに1商品・バリアントはこの順）
  1. Light     ¥51,000    ← LIGHT PLAN ライトプラン：花束のみ
  2. Standard  ¥128,000   ← STANDARD PLAN スタンダードプラン：花束＋写真撮影（予約フォームの初期選択）
  3. Luxury    ¥228,000   ← LUXURY PLAN ラグジュアリープラン：花束＋写真撮影＋動画撮影＋デコレーション

追加商品（全ロケーション共通、各1バリアント。自動コレクション propose-options）
  PRIVATE TRANSFER 専用送迎 ¥30,000   ← requires_hotel：選ぶと予約者情報に「滞在ホテル」欄が出る
  EXTRA PHOTO 追加撮影30分  ¥20,000   ← requires_photo：ライトプランでは選べない
  SUNSET TIME ベストタイム確保 ¥10,000
```

- 金額はすべて仮の値です（モックアップではライト＝スタンダードの約4割、ラグジュアリー＝スタンダード＋¥100,000 で仮置き）。
- 各プランに含まれるものは、メタオブジェクト `propose_settings` の `light_includes` / `standard_includes` / `luxury_includes` で管理。
- 当日の5ステップ（フォトグラファーとの待ち合わせ〜記念撮影）は写真撮影付きプランの流れなので、その旨を注記しています。

### 3.2.1 プロポーズの場所

場所は **6 種類で固定**（ビーチ／チャペル／教会／モニュメント／レストラン／ホテル）。旅行先ごとに「選べる種類」と、
種類ごとの「会場名（任意）」を持ちます。種類の表示名と説明文は `snippets/propose-place-type.liquid`。

| メタオブジェクトのフィールド | 役割 |
|---|---|
| `place_types`（リスト） | 選べる種類（`beach` など）。会場名がない種類もここで有効にする |
| `beach_venues` `chapel_venues` `church_venues` `monument_venues` `restaurant_venues` `hotel_venues`（各リスト） | 会場名。入れた種類は自動で「選べる」扱い |

表示する場所（オススメの入れ方）:
1. **TOP の旅行先カード** — 都市名の下に「ビーチ・チャペル・ホテル」と選べる場所を小さく表示
2. **TOP「ビーチでも、チャペルでも。」** — 種類ごとの行に、選べる都市を並べる。押すと `?place=chapel` 付きで旅行先ページへ
3. **旅行先ページ「どこで伝えますか？」** — おまかせ＋選べる種類をボタンで選択。説明と会場名を表示し、

4. **予約フォーム「場所」ステップ**（時間の次） — 種類 →（会場名があれば）会場 → ご希望の自由記入。
   旅行先ページで選んで来た場合はこのステップを飛ばし、上部のチップ「変更」で戻れる

| 場所 | 旅行先（初期データ） |

### 3.3 受付状況の扱い（リクエスト制）

フォトグラファーの手配はその場で確定できないため、カレンダーは「空いている」ではなく
**「申し込めるかどうか」の目安** として表示します。

| 状態 | 表示 | 意味 |
|---|---|---|
| available | ◎ 受付中 / OPEN | リクエストできる |
| few | △ 残りわずか / FEW LEFT | `few_left_slots` に入っている枠 |
| soldout | × 受付終了 / FULL | `blocked_slots` に入っている枠（選べない） |
| closed | ― 締切 / CLOSED | `lead_time` 以内の日（自動） |

1. **当面**: `blocked_slots` / `few_left_slots` を運営が管理画面で更新（本当に埋まっている枠だけを入れる。
   ダミーの状況は作らない）。
2. **拡張**: 予約管理システムやスタッフのシフト表とつなぎ、Flow／Webhookで上記2フィールドを自動更新。

「受付中」でも確定ではありません。確定は運営がリクエストを確認してから行います。
返信までの時間（モックアップでは24時間・仮の値）はメタオブジェクト `propose_settings`（1件）の `reply_hours` に置き、
画面の各所（Last Minute・受付締切・予約フロー・完了画面・FAQ）で同じ値を表示します。
予約者は「希望の時間が難しい場合、同じ日の別の時間でもよい」にチェックできます（代替案の提示を早くするため）。

### 3.4 リクエストの受け取りとお支払い

お支払いは **確定のあと** にします。Shopify標準機能での推奨構成:

1. **リクエスト送信** — 予約フローの最後で、Shopify標準のお問い合わせフォーム（`{% form 'contact' %}`）に
   `contact[location]` / `[plan]` / `[options]` / `[date]` / `[time]` / `[flexible]` / `[hotel]` / `[surprise]` /
   `[total]` を入れて送信。運営にメールが届きます（アプリ不要・カード情報は受け取らない）。
2. **確認** — 運営がフォトグラファーの手配を確認し、`reply_hours` 以内に返信。
3. **確定とお支払い** — 管理画面で **下書き注文**（Draft order）を作成し、プラン商品のバリアント＋追加商品を入れて
   line item properties（`LOCATION` / `PLAN` / `DATE` / `TIME` / `Meeting Point` / `Hotel`）を付け、
   「請求書を送信」。お客様はメールのリンクから支払い、支払い完了で注文＝予約確定。
   この時点で `blocked_slots` を更新します。
4. **難しい場合** — 近い日時を提案するメールを送る（下書き注文は作らない）。

サプライズ配慮の希望があれば、1〜3のメールはすべて控えめな件名で送ります
（請求書メールは通知テンプレートで `draft_order` の属性から件名を切り替え）。

代替案: 直前の申し込みで支払いまでを一度に済ませたい場合は、Checkout で決済を **手動キャプチャ**（与信のみ）に設定し、
確定時にキャプチャ、不可ならキャンセルする方法もあります。ただし与信の有効期限（通常7日程度）内に確定する必要があり、
「確定前にカード情報を入れる」ことになるため、モックアップは1〜4の構成に合わせています。

## 4. 画面設計（v2.2・これからプロポーズする男性の目線で再設計）

考え方は `UX-AUDIT.md`（検証レポート）にまとめています。要点：
「どこでできる？→どんな一日？→いくら？→間に合う？→バレない？」の順に、**1つの事実は1か所だけ** に置く。
場所（ビーチ・チャペルなど）は、TOP でも旅行先ページでも **最初の選択肢** として大きく見せる。

### TOP `/pages/propose`
1. **Hero** — 全画面写真／「世界で、忘れられないプロポーズを。」／CTA「旅行先から探す」＋リンク「場所（ビーチ・チャペルなど）から探す」
2. **安心のポイント**（ヒーロー直下・4項目）— 最短○日前まで／24時間以内に確定のご連絡／お支払いは確定後／サプライズ配慮
3. **Destinations**（主役）— 見出し → **「プロポーズしたい場所は？」6つのアイコンタイル**（各「○か所」）→ 旅行先カード（12件）。
   タイルを押すと、その場所でできる旅行先だけに絞り込み、カードに会場名（例：教会 キャルバリー・バイ・ザ・シー教会）を表示。
   カードの価格は「写真付き ¥〜」と「花束のみ ¥〜」の2本（花束のみの価格だけを「From」にしない）
4. **Your Proposal** — 当日の5ステップ（文章のみ。写真は上のカードと重複するため使わない）
5. **Plan** — 3プランを **1つの比較表**（行＝プラン、列＝花束／写真／動画／装飾／料金）＋オプション
6. **FAQ** — 5問表示、残りは「すべての質問を見る」
7. 締めのCTA／フッター（全旅行先へのリンク）。スマホは下部固定「旅行先から探す」

（以前あった「Last Minute」「Place」「Not Decided Yet」の3セクションは、上の 2・3 に統合して廃止）

### ロケーション詳細 `/pages/propose/<handle>`（最重要）
1. **Hero** — 写真／H1「ハワイで、一生忘れないプロポーズを。」／価格「花束のみ ¥〜」「写真付き ¥〜」／CTA「場所を選ぶ」「日程を確認する」
2. **About＋安心の4項目** — 紹介文と、受付期限／確定のご連絡／お支払い／サプライズ（ここで初めて出す。以降は繰り返さない）
3. **Place（場所カード）** — 「ハワイの、プロポーズ場所を選ぶ。」選べる場所を **大きなカード**（アイコン・名前・一言・会場名）で。
   選ぶと詳細を表示し、ページ内の予約リンクすべてに `&place=` が付いて予約に引き継がれる。選ばなくてもよい（おまかせ）
4. **Your Proposal** — 5ステップ（写真は使わない。冒頭の写真と重複するため）
5. **Plan** — 比較表＋オプション＋CTA
6. **Availability** — 今日から14日間→日付→時間→「この日時で申し込む」。すぐ下に「雨の日」の一文（不安が生まれる場所に置く）
7. **FAQ** — 気づかれない？／雨は？／すぐ確定？／写真なしでも？／キャンセル／指輪・花束。ここでしか出ない質問だけ
8. **締めのCTA** — 写真は冒頭と別の位置で切り出す。ほかの旅行先へのリンク。スマホは下部固定「写真付き ¥〜｜この場所で予約する」

### 予約フロー `/pages/propose-booking`
- ステップ: `[旅行先] → 日にち・時間 → 場所 → プラン・オプション → お客様情報 → 確認`（日付と時間は1画面。日にちを選ぶと同じ画面に時間が出る）
- 旅行先ページで選んだもの（場所・日時）はスキップ。場所と日時を選んで来た場合は「プラン・オプション」から始まり、残りは3画面
- 上部に「STEP 2 / 5 ○○」と進捗バー、右側に常に「お支払いは確定後」。選択済み内容はチップ表示（「変更」で戻れる）
- 場所は「おまかせ」がいつでも選べる（選ぶと自動で次へ）。会場名がある場所では会場も指定でき、自由記入欄がある
- プランはスタンダードが初期選択。オプションはチェックで追加（追加撮影は写真付きプランのみ）
- お客様情報は最小限（お名前・メール・任意の電話・送迎時のみホテル）＋サプライズ配慮＋時間の融通＋規約同意
- 最後は「リクエスト内容の確認」→「予約をリクエストする」。お支払いは発生しないことを明記。まとめの項目名はすべて日本語
- 完了画面は「リクエストを受け付けました」。まだ確定していないこと・返信の期限・確定後の支払い方法を順に案内

## 5. デザインルール

- 色: paper `#faf9f6` / paper-deep `#f2efe8` / ink `#161512` / gold `#a3803f`。
  ゴールドは英字ラベルと細い区切りのみ。ボタンは黒（写真の上は白）。黒背景＋金文字で高級感を出さない。
- 書体: 英字 Cormorant Garamond（ラベル・地名・価格）、日本語 Noto Sans JP（見出し500／本文300）。
- 見出しは必ず「英字ラベル → 日本語見出し（1〜2行）→ 短い説明（2〜3行まで）」の3階層。
- カードUIは Destinations のみ。ほかは写真と余白、罫線で区切る。
- アニメーションはフェード＋わずかな移動と写真のゆっくりしたズームのみ。スマホでは移動なし、
  `prefers-reduced-motion` で全停止。

## 8. 写真について

- 10か所はご提供の写真を使用しています（ハワイは透かしなしの差し替え版）。沖縄本島・グアムは写真未提供のため、イラストの仮表示です。
- **TOPのHero**: 指示書の「プロポーズ直前・プロポーズ中の一瞬」（人物が写った写真）が未提供のため、
  現在はカッパドキアの風景写真を使用しています。
- 差し替え方法（モックアップ）: `propose-lp/images/<ロケーションID>.jpg` を置いて `python3 propose-lp/build.py`。
  写真がない場所は自動でイラスト表示になります。
