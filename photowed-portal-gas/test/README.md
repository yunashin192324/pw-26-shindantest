# 動作テスト（開発者向け）

Google Apps Script の実行環境（SpreadsheetApp / MailApp / CacheService など）を
Node.js 上で模擬して、`Code.gs` のロジックを実際に動かして検証するテストです。
スプレッドシートやデプロイは不要で、手元ですぐ実行できます。

### まとめて実行する（推奨）

```bash
cd photowed-portal-gas/test
npm install --no-save jsdom   # 初回のみ（画面テストに必要）
node run_all.js
```

`合計: 404 件成功 / 0 件失敗` と表示されれば正常です。
テストは3種類あり、それぞれ役割が違います。

| ファイル | 役割 | 件数 |
|---|---|---|
| `gas_test.js` | 個々の機能が仕様どおり動くか | 244 |
| `audit_test.js` | 全APIが例外なく守られているか（認可・セッション・ロック・異常入力） | 123 |
| `ui_test.js` | 画面を実際に描画して操作できるか | 37 |

### 個別に実行する

```bash
node gas_test.js
```

`結果: 244 件成功 / 0 件失敗` と表示されれば正常です。

## 全API横断の監査テスト（`audit_test.js`）

「個々の機能が動くか」ではなく「**全てのAPIが例外なく守られているか**」を総当たりで確認します。
新しいAPIを追加して保護を書き忘れた場合、このテストが落ちて気づけるようになっています。

| # | 項目 |
|---|---|
| A1 | 認可マトリクス（新設APIの登録漏れ・認証/JP判定/可視性チェック/ロックの書き忘れを検出） |
| A2 | 支店データ分離（全APIに対して他支店のデータを実際に触らせてみる） |
| A3 | 既読チェックの認可（履歴IDを知られても他支店を操作できない） |
| A4 | セッション（未指定・空・null・偽造・数値・オブジェクト・期限切れ・ログアウト後を全APIが拒否） |
| A5 | ロック競合（書き込みAPIが競合時に分かりやすく失敗し、ロックを漏らさない） |
| A6 | 異常入力のファズ（1,265通り。内部エラーが利用者に露出しないこと） |
| A7 | データ側の異常（案件0件・不正な日付文字列でも画面と定期処理が落ちない） |
| A8 | ログインの総当たり対策（連続失敗で一時停止・他支店に波及しない・時間で自動解除） |
| A9 | 日付は認識できないなら保存しない（静かにアラート対象から消える事故の防止） |
| A10 | 外部サイトへのiframe埋め込みを許可していないこと |
| A11 | 保存の原子性（1項目でも不正なら何も書き込まない） |
| A12 | 日本側と支店の同時編集（互いの変更を消し合わない・上書きも履歴に残る） |

## 注意

`gas_harness.js` はテスト用の簡易モックであり、Apps Script の完全な再現ではありません
（日付のタイムゾーン処理などは簡略化しています）。ロジックの回帰チェック用途に使ってください。
`Code.gs` を修正したら、`node run_all.js` を実行してから反映することをおすすめします。

なお `gas_harness.js` は Node の `vm` で別realmを作るため、**シートに入れる日付は必ず
`ctx.__newDate` / `ctx.__daysFromToday` か `Utilities.parseDate` 経由で作ってください。**
テストコード側で素の `new Date()` を使うと `instanceof Date` が false になり、
実際には動く／動かないに関わらずテスト結果が信用できなくなります。
